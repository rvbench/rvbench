# 运行时边界实施计划

- 日期：2026-11-02
- 设计：`docs/specs/2026-11-02-runtime边界-设计与接口.md`
- 图：`documents/架构图/05-runtime-boundary.svg`、`06-runtime-sequence.svg`
- 范围：P0 + P1（协议、worker、manager、cli）。P2 另起一轮，P3 等一个稳定版本。

## 0. 本轮做完什么算完成

1. wire 正本接受 `runtime` / `source_kind` / `entry` / `suite` / `case`，`implementation` 标废弃。
2. `WorkerRegistration` 接受 `contexts[]` / `runtimes[]` / `slots[]`。
3. 协议仓提供 `admit()`、`runtime_ref()`、`Placement`、`RejectReason`，老路径保持行为不变。
4. worker 把能力表从 `backend.rs` 的 if/else 挪进两个 provider，注册时声明 `runtimes` 与 `slots`。
5. manager 用 `admit()` 派发，新增 `GET /runtimes`、`GET /runtimes/{id}`，结果带 runtime 指纹。
6. cli 提供 `--runtime` / `--source-kind` / `--entry` / `--legacy`。
7. 四个仓 `cargo test` 全绿；主仓 `cargo run -p rvbench-tools -- check` 通过。

不做：P2 的榜单重排、`ruyiai-sdk` provider 实装、任何线上部署。

## 3. 验收口径

- `cargo test` 不只跑通，还要覆盖：runtime 未装、版本钉不匹配、方言不支持、老 worker 回退。
- 老请求（只有 `implementation`、没有 `runtimes[]`）行为逐字节不变，`request_sha256` 不受影响。
- 任何声明缺失都必须降级到 legacy 路径，不能直接拒绝整台 worker。

## 4. 风险

| 风险 | 处理 |
|---|---|
| 三个仓同时改，rev 钉错乱 | W1 统一 path 依赖，W2 一次性还原 |
| worker 重构引入行为漂移 | provider 只搬代码不改参数；现有测试不改断言 |
| manager 目录端点与 console 口径分叉 | `runtime_dtypes` 抽成公共函数，两处共用 |
| cli 新参数被老 manager 拒 | `--legacy` 保留旧写法，默认不破坏 |

## 5. 回滚

单仓 `git revert` 即可。协议加的都是可选字段，老客户端不受影响；唯一的行为开关是 `admit()`，manager 回滚后自动退回 `worker_supports_request`。

## 6. W2 合流清单

按顺序执行，任一步失败就停：

1. 三仓 `cargo test` 全绿（worker / manager / cli）。
2. `python tools/sync_cli.py` 再跑一次，确认 cli 的 `contracts/` 与正本一致。
3. 三仓把 `rvbench-protocol = { path = "../rvbench-core-rust" }` 还原成 rev 钉，rev 取协议仓本轮提交 sha。
4. `cargo run -p rvbench-tools -- check`（主仓）。
5. 主仓 `tools` 的两个 pin 若与本轮不一致，单独记一笔依赖债，不在本轮强推。

还原 rev 钉之前先确认协议仓提交已在远端存在，否则 `cargo` 取不到。
