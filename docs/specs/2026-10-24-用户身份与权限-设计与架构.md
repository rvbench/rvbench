# 用户身份与权限：设计与架构

状态：**草案（待评审）** ｜ 涉及四个仓 ｜ 目标：GitHub 登录 + 角色派生 + 分级授权

实现计划：[用户体系（前后端）](../plans/2026-10-24-用户体系-前后端实现计划.md) · [worker 认证与权限（前后端）](../plans/2026-10-24-worker认证与权限-前后端实现计划.md)

本文定义 rvbench 的用户体系：谁能提交算子任务、谁能发布 suite、worker 如何认证、manager 如何在**不破坏现有无认证部署**的前提下逐步收紧。接口草案见 [contracts/api/proposals/2026-10-24-auth.openapi.yaml](../../contracts/api/proposals/2026-10-24-auth.openapi.yaml)。

先回答两个前置问题。

## 0. 一页结论

**Q1：GitHub 是 OIDC 吗？**

不是。`https://github.com/.well-known/openid-configuration` 返回 404；GitHub 只提供 OAuth 2.0（authorization code / device flow）。GitHub Actions 的 OIDC 是给 workflow 签发 id_token 让云厂商联邦，与"用户登录第三方应用"是两件事。

所以"用 OIDC 接 GitHub"有三种落地方式：

| 方案 | 组件 | 配置成本 | 换来什么 | 结论 |
|---|---|---|---|---|
| A. manager 内建 OAuth2 adapter | 无新增 | 一个 OAuth App | 最快；provider 抽象仍是 OIDC 形状 | **v1 采用** |
| B. 部署 Dex（GitHub connector） | +1 组件 +1 跳 | App + Dex 配置 + 证书 | 真 OIDC（discovery/JWKS/id_token），以后换 Google/企业 SSO 零改动 | v1.1 备选 |
| C. 复用现有 auth.c4y.dev | 取决于它是什么 | — | 可能最省 | **不可用**：该域名当前 DNS 不解析 |

v1 的实现仍然按 OIDC 的形状抽象（`IdentityProvider` trait：`authorize_url` / `exchange` / `userinfo` / `team_membership`），GitHub 是第一个 adapter。将来上 Dex 只加一个 `OidcProvider`，业务与角色代码不动。

**Q2：先做用户系统，suites 会不会更方便？**

会，而且省掉的正是 suites 设计里最别扭的部分：

| suites 原设计 | 有用户系统后 | 净效果 |
|---|---|---|
| 单一 `admin_token` | 删除，改 `suite:publish` 权限 | 少一套 token 分发/轮换/不进日志的规矩 |
| `suite_id` 的 owner 由客户端自报 | 从 `sub` 派生，客户端不能指定 | 防冒名；配额才真正生效 |
| 配额按自报 owner | 按 `sub` | 无法靠改 owner 绕过 |
| `created_by: "c4y"` 字符串 | `{sub, login, login_at_publish}` | 改名可追、退组可追溯 |
| `GET /suite-runs/{id}` 公开 | 仅 owner / admin | 别人的实现与结果不可窥探 |
| 无审计 | publish / run / cancel 全记 | 出事可查 |

代价只有两条：CLI 多一步 `rvbench auth login`；测试要 mock provider。**结论：先做用户系统，suites 文档按第 13 节改 6 处。**

**分三期发布**（关键：worker token 不依赖 GitHub，可以最先落地）：

| 期 | 内容 | 外部依赖 | 可独立发布 |
|---|---|---|---|
| P0 | `auth.mode` 三级开关 + worker token | 无 | 是 |
| P1 | GitHub 登录 + 角色派生 + 端点授权 | GitHub OAuth App | 是 |
| P2 | 自定义 suite（见另一份 spec） | P1 | 是 |

## 1. 现状

| 事实 | 影响 |
|---|---|
| manager v1 全仓无认证（`contracts/api/openapi.json` 的 `security: []`） | 任何人可 `POST /jobs`、读 `/results`、注册假 worker |
| `POST /cluster/workers/register` 无需凭据 | 可注册假 worker 抢单，再返回伪造结果 |
| worker 对 manager 的 5 处请求（register / claim / ack / renew / events）**不带任何 header** | 不能简单前置 basicAuth，必须改 worker 或走路径密钥 |
| manager 单快照 `Store<ManagerData>`（`control_state` 一行 JSON） | session/审计不能塞进去，否则每次 job 事务都重写全部会话 |
| 公网入口 `https://rvbench.hk.c4y.dev` 已通（Traefik → EndpointSlice → tailnet） | OAuth 回调地址可固定，不需要新暴露面 |
| 无速率限制 | 登录端点需要单独限流，否则可被刷 |

## 2. 角色与权限

角色**派生**，不存储、不可手工授予（`admins` 除外）。

| 角色 | 判定 | 说明 |
|---|---|---|
| `anonymous` | 未登录 | 只能读公开资源 |
| `user` | 任何 GitHub 账号登录成功 | 提交算子任务、看自己的任务 |
| `early_access` | 属于 `rvbench` 组织的 `EarlyAccessDevelopers` 团队（`state=active`） | 发布 suite、提交 suite run。**隐含 `user`** |
| `admin` | 配置 `auth.admins` 里的 **`sub`**（`github:<id>`） | 运维：看全部、撤销会话、drain worker。不用 login：login 可改名，旧名还能被他人抢注 |
| `worker` | 持有 `worker_tokens[]` 中某条有效凭据的机器 | 注册、领任务、回报。**与 `user` 互斥**：机器不登录，人不用 worker token |

角色是集合而非单值：`admin` 不必是 `early_access`，但实现上把 `admin` 视为包含全部权限。「累积」的具体含义：任何登录用户都有 `user`；`early_access` 与 `admin` 是叠加项。所以 `roles` 可能是 `["user","early_access","admin"]`，`/auth/me` 的 `permissions` 是这些角色对应权限的并集。

`worker` 不参与累积：它是另一种主体（机器），不会与 `user` / `early_access` / `admin` 同时出现。

**权限点**（编译期枚举，端点绑定）

| 权限 | anonymous | user | early_access | admin | worker |
|---|---|---|---|---|---|
| `public:read`（`/healthz` `/ui` `/leaderboard` `/results`） | ✓ | ✓ | ✓ | ✓ | ✓ |
| `metrics:read` | 可配（默认 ✓） | ✓ | ✓ | ✓ | ✗ |
| `job:submit` | ✗ | ✓ | ✓ | ✓ | ✗ |
| `job:read:self` | ✗ | ✓ | ✓ | ✓ | ✗ |
| `job:read:all` | ✗ | ✗ | ✗ | ✓ | ✗ |
| `job:cancel:self` | ✗ | ✓ | ✓ | ✓ | ✗ |
| `suite:publish` | ✗ | ✗ | ✓ | ✓ | ✗ |
| `suite:run` | ✗ | ✗ | ✓ | ✓ | ✗ |
| `suite:read:self` | ✗ | ✗ | ✓ | ✓ | ✗ |
| `suite:read:all` | ✗ | ✗ | ✗ | ✓ | ✗ |
| `worker:create:self`（private，归属自己） | ✗ | ✓ | ✓ | ✓ | ✗ |
| `worker:create:public`（归属组织） | ✗ | ✗ | ✗ | ✓ | ✗ |
| `worker:register` | ✗ | ✗ | ✗ | ✗ | ✓ |
| `worker:execute`（claim / ack / renew / events） | ✗ | ✗ | ✗ | ✗ | ✓ |
| `worker:manage:self`（drain / 删除 / 轮换自己的） | ✗ | ✓ | ✓ | ✓ | ✓（只能撤销自己） |
| `worker:manage:all` | ✗ | ✗ | ✗ | ✓ | ✗ |
| `session:revoke` | ✗ | 自己 | 自己 | 全部 | ✗ |

**worker 主体**

```json
{"sub": "worker:k3-1", "login": "k3-1", "provider": "worker", "roles": ["worker"]}
```

| 规则 | 说明 |
|---|---|
| `sub` 前缀 | `worker:<worker_id>`，与 `github:<id>` 区分；`provider` 为 `worker` |
| token 与 id 绑定 | 凭据条目的 `id` 必须等于 `register` 请求里的 `worker_id`，否则 403（防一个 token 注册多个 worker） |
| owner / visibility 不由 worker 声明 | 由 token 对应的 worker 记录决定（创建时写入）。`WorkerRegistration` 里没有这两个字段，worker 也无法自封 public |
| 与用户互斥 | 一次请求只解析一种凭据：Bearer `rvb_`/cookie → 人；Bearer worker token → 机器。worker token 不产生 `user` 角色 |
| 自我撤销 | worker 的 `worker:manage:self` 只能作用于自己的记录（`DELETE /workers/{自己}`）；删除别人的 worker 要 `worker:manage:all` |
| 不给 admin `worker:execute` | 人不能冒充机器抢单，否则调度归属与审计都会错位 |
| 通道开关 | `worker_tokens` 为空 → `/cluster/*` 放行（灰度）；非空 → 强制。与 `auth.mode` 独立 |

**worker 归属**

每台 worker 有一条记录，注册时按 token 查到它，把 owner 与 visibility 带进主体：

```json
{
  "worker_id": "k3-4",
  "owner": {"sub": "github:1234567", "login": "c4y"},
  "visibility": "private",
  "status": "active",
  "token_prefix": "rvbw_7f3c",
  "created_at": "2026-10-24T07:10:00Z"
}
```

| 字段 | 取值 | 谁能设 |
|---|---|---|
| `owner` | 创建者的 `sub`；public worker 固定 `org:rvbench` | 由创建者身份决定，不可自报 |
| `visibility` | `private`（默认） / `public` | `private`：任何登录用户；`public`：仅 admin |
| `status` | `pending`（已创建未注册） / `active` / `revoked` | 服务端维护 |

**可见性与调度**（这是"私有"的实际含义，两处都要生效）：

| 场景 | private | public |
|---|---|---|
| `GET /workers` 列表 | 仅 owner 与 admin 可见 | 所有人（含匿名，仅运行时状态） |
| 被分配 job | **只接 `owners[job] == worker.owner.sub` 的任务** | 所有任务 |
| drain / 删除 / 轮换 token | owner 或 admin | 仅 admin |

`owners[job]` 缺失（升级前提交的 job）时，只调度到 public worker——安全默认，不会把历史任务漏给别人的私有板。

**注册路径**

一台板子拿到 token 有三条路，最终都落到同一条 worker 记录：

| 路径 | 谁发起 | 凭据 | 适用 |
|---|---|---|---|
| bootstrap 配置 | admin 预置 | 配置文件 `worker_tokens[]` | 集群初始化、无用户系统时 |
| 预置签发 | 用户已登录，`POST /workers` | 返回一次性 `rvbw_` token，手工配到板子 | 运维批量、CI、长期在役 |
| **首次认领（claim）** | **worker 发起，用户在浏览器确认** | 短码 + 一次性 device_code | 用户自己上板、不想手工搬 token |

**首次认领（claim）**

这条路径解决的是"token 怎么安全地落到板子上"：不让用户复制粘贴一长串密钥，而是让板子自己领。

```
worker（无 token 启动）                    manager                       用户浏览器
  │ POST /cluster/workers/claim             │                              │
  │ {worker_id, board_id, backend, kinds}   │                              │
  ├────────────────────────────────────────▶│ 限流 + worker_id 冲突检查     │
  │◀── {code:"K3F9-Q2T4", device_code,      │ 写 worker_claims(pending)     │
  │      verification_url, expires_in:600}   │                              │
  │ 打印：打开 https://…/claim 输入 K3F9-Q2T4 │                              │
  │                                          │◀── GET /claims（登录）────────│
  │                                          │── 列出待确认（含来源 IP）─────▶│
  │                                          │◀── POST /claims/{code}/approve│
  │                                          │    {visibility:"private"}     │
  │                                          │ 建 worker 记录，owner=当前用户 │
  │                                          │ 签发 token（存 sha256）        │
  │ 每 5s GET /cluster/workers/claim/{dev}   │                              │
  ├────────────────────────────────────────▶│                              │
  │◀── 200 {token:"rvbw_…"}（一次性）         │                              │
  │ 落盘 0600，转正常注册                      │                              │
```

| 状态 | 触发 | worker 轮询结果 |
|---|---|---|
| `pending` | worker 提交 claim | 202 |
| `approved` | 用户确认 | 200 + token（只返回一次，随后清空） |
| `denied` | 用户拒绝 | 410 |
| `expired` | 10 分钟未确认 | 410 |

约束：

| 项 | 规则 |
|---|---|
| code | 8 字符 `XXXX-XXXX`，去掉 `0/O/1/I`；全局唯一；只在确认页出现 |
| device_code | 32 字节随机，只有发起 claim 的 worker 持有；轮询凭它，不凭 code |
| 有效期 | 10 分钟；过期记录 24h 后清理 |
| 限流 | 每 IP 5 次/分钟；全局待确认上限 20 |
| `worker_id` 冲突 | 已被 active 记录占用 → claim 直接 409，不进入确认 |
| owner 来源 | **确认者的会话**，不是 claim 请求里的字段；worker 无法指定归属 |
| 确认页展示 | worker_id、board_id、backend、kinds、来源 IP、请求时间，并提示「只在你亲自上架时确认」 |
| 重复确认 | 第二个确认者 409，先到先得 |

`approve` 复用 `worker:create:self`（public 复用 `worker:create:public`），不新增权限。确认动作本身记审计 `worker.claim.approve`。

**token 生命周期**

| 动作 | 端点 | 说明 |
|---|---|---|
| 创建 | `POST /workers` | 返回 `rvbw_…` 明文，**只显示一次**；库里存 sha256 与前缀 |
| 认领 | `POST /claims/{code}/approve` | 同上，但 token 由 worker 轮询取走，不经过人手 |
| 轮换 | `POST /workers/{id}/tokens` | 旧 token 立即失效，返回新明文；在役 worker 下次请求 401，需重配 |
| 撤销 | `DELETE /workers/{id}` | 有在途 assignment 返回 409；无在途则标记 `revoked` 并清 token |

worker 侧配置项仍是一个 `manager_token`，不需要知道自己的 owner。`manager_token` 为空且 `allow_claim=true`（默认）时进入认领模式；`allow_claim=false` 时启动即失败并打印配置指引。

owner 不进 `Principal`：审计要 owner 时按 `worker_id` 回查记录即可；把它塞进主体容易让"机器"看起来像"人"，权限判断会误用。suite run 展开出的 job，`owners[job]` 是 run 的提交者，所以用户的私有 worker 天然能跑自己的 suite，跑不了别人的。

**`/cluster/*` 路由与权限**

| 路由 | 权限 |
|---|---|
| `POST /cluster/workers/register` | `worker:register` |
| `POST /cluster/assignments/claim` | `worker:execute` |
| `POST /cluster/assignments/{id}/ack` | `worker:execute` |
| `POST /cluster/assignments/{id}/events` | `worker:execute` |
| `POST /cluster/leases/{id}/renew` | `worker:execute` |
| `GET /cluster/workers` | 匿名只看 `public`；登录后加上自己的 `private`；响应去掉 `url`，admin 可 `?full=true` 取完整 |
| `POST /cluster/workers/{id}/drain` | owner（`worker:manage:self`）或 admin（`worker:manage:all`） |
| `POST /cluster/workers/claim` | 无凭据（限流），仅 `auth.mode != off` 时可用 |
| `GET /cluster/workers/claim/{device_code}` | 无凭据（device_code 即凭据），仅 `auth.mode != off` 时可用 |

`job:read:self` 需要归属：manager 在 `ManagerData` 新增 `owners: BTreeMap<job_id, sub>`，与 job 同事务写入。不改 `JobRecord` 协议。

**资源级归属**（中间件之后在 handler 内二次判断，中间件拿不到资源 id）：

| 端点 | 规则 |
|---|---|
| `GET /jobs` | `user` 只返回 `owners[job] == sub` 的；admin 返回全部 |
| `GET /jobs/{id}` | owner 或 `job:read:all`；否则 **404**（不用 403，避免枚举 job id） |
| `DELETE /jobs/{id}` | owner 或 admin |
| `GET /suites/{owner}/{name}` | `owner == "rvbench"` 公开；否则须为 owner 或 admin |
| `GET /suite-runs/{id}` | owner 或 `suite:read:all` |

官方 suite（`owner=rvbench`）的读端点公开，是为了让 benchmark 定义本身可被引用与审计；写与运行仍然要 `early_access`。

**worker 管理端点**

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| `POST` | `/workers` | `worker:create:self` / `worker:create:public` | body `{worker_id, visibility}`；返回一次性 `rvbw_` token |
| `GET` | `/workers` | 登录用户 | 自己的 + public；admin 全部。含 `pending` 记录 |
| `GET` | `/workers/{id}` | owner / admin | 记录详情（不含 token） |
| `DELETE` | `/workers/{id}` | owner / admin | 有在途 assignment → 409 |
| `POST` | `/workers/{id}/tokens` | owner / admin | 轮换，旧 token 立即失效 |
| `GET` | `/claims` | 登录用户 | 待确认的 claim（worker_id / board / 来源 IP / 过期时间） |
| `POST` | `/claims/{code}/approve` | `worker:create:self`（`public` 要 `worker:create:public`） | 绑定 owner 并签发 token |
| `POST` | `/claims/{code}/deny` | 登录用户 | 拒绝，worker 轮询得 410 |

`POST /workers` 与 `POST /cluster/workers/register` 是两件事：前者是**人**建记录、发 token；后者是**机器**拿 token 注册运行时。没有记录就没有 token，没有 token 就注册不上（`worker_tokens` 为空且 `auth.mode=off` 的灰度期除外）。

## 3. 设计决策

### D1：`admin_token` 不进入长期方案

suites 草案里的 `admin_token` 是一次性权宜。用户系统落地后直接删除该字段，改由 `suite:publish` 权限判定。**不要**两套并存——并存就会出现"token 绕过角色"的隐性后门。

### D2：GitHub 走 OAuth2，接口按 OIDC 抽象

```rust
trait IdentityProvider {
    fn authorize_url(&self, state: &str, pkce: Option<&Pkce>) -> String;
    fn exchange_code(&self, code: &str, pkce: Option<&Pkce>) -> Result<ProviderToken>;
    fn userinfo(&self, token: &ProviderToken) -> Result<ProviderUser>;   // sub, login, name, email, avatar
    fn team_membership(&self, login: &str, org: &str, team: &str) -> Result<Membership>; // active|pending|absent
}
```

`ProviderUser.sub` 必须是稳定标识：GitHub 用 `id`（数字），拼成 `github:<id>`。**不用 login**——login 可改名，改名后会话会漂移。

`provider.kind` 枚举：`github`（v1）、`oidc`（v1.1，Dex/Keycloak）、`static`（测试/本地开发）。

### D3：角色实时派生 + 5 分钟缓存，失败降级不 fail-open

每次请求按 `sub` 查 `role_cache`：

| 缓存状态 | 行为 |
|---|---|
| 命中且未过期 | 直接用 |
| 未命中/过期 | 调 provider 查 team，成功则刷新 |
| provider 5xx/超时 | **降级为 `user`**（保留 `job:submit`，收回 `suite:*`），`/auth/me` 标 `roles_stale=true`，缓存 60s 后再试 |

不 fail-open（GitHub 挂了就给所有人 suite 权限），也不 fail-closed（把所有人踢下线，连 job 都提交不了）。因为 `user` 是"登录即得"、不依赖实时校验，降级只影响 suite 权限。

### D4：两种会话，一套主体

| 客户端 | 凭据 | 传输 | 有效期 |
|---|---|---|---|
| 浏览器（`/ui`） | `rvb_session` cookie | `HttpOnly; Secure; SameSite=Lax; Path=/` | 12h 滑动 |
| CLI / 脚本 | `rvb_<32B base64url>` | `Authorization: Bearer` | 30d 固定，可撤销 |

两者在 `sessions` 表里同构，只差 `kind`。token 明文只在签发时返回一次，库里存 `sha256`。前缀 `rvb_` 便于 GitHub secret scanning 与日志脱敏。

### D5：CLI 用 device flow，不新增本地回调服务

GitHub OAuth App 支持 device flow（需在 App 设置里勾选 Enable Device Flow），且**只要 client_id**。流程：

```
CLI ──POST github.com/login/device/code──▶ 拿到 user_code + device_code
CLI 打印 https://github.com/login/device 与 user_code
CLI ──轮询 github.com/login/oauth/access_token──▶ 拿到 GitHub access_token
CLI ──POST /auth/github/exchange {access_token}──▶ manager 校验并签发 rvb_ token
CLI 丢弃 GitHub token，只存 rvb_ token（0600，~/.config/rvbench/credentials）
```

比 loopback 回调简单（不用临时起 HTTP server、不用担心端口/防火墙），也比 manager 代理轮询简单。代价是 CLI 短暂持有 GitHub token；它只在内存里，换完即弃。

### D6：worker 用独立凭据，但作为一等角色

`cluster/*` 是机器通道。新增 `worker` 角色与 `worker_tokens[]`（每台 worker 一条 `{id, sha256}`），worker 的 5 处请求带 `Authorization: Bearer <worker_token>`，worker 侧配置项为 `manager_token`。

**凭据独立，授权统一**。凭据不经过 GitHub、不产生 cookie；但判定必须和用户走同一个中间件。否则 `worker:register` / `worker:execute` 的检查会散落在 5 个 handler 里，审计也没有 `sub` 可落。进角色表后：

- 中间件一处判定，权限矩阵一张表看完（§2）。
- 审计可以记到具体机器：`sub=worker:k3-1`，而不是一句"某个持有 token 的客户端"。
- `GET /cluster/workers` 能保持公开，`drain` 单独要 `worker:manage`，不会因为加了认证把 console 打坏。

主体形状与约束见 §2「worker 主体」。不采用"路径前缀密钥 + StripPrefix"：密钥会进 URL、日志与抓包；改 worker 代码加 header 只有 5 行。

轮换：数组允许新旧并存，重载配置即可（v1 重启）。

`worker_tokens[]` 只作为 **bootstrap**：留给集群初始化（三块板子、无用户系统时），条目固定 `owner=org:rvbench`、`visibility=public`。用户自助创建走 `POST /workers`，token 入库（存 sha256），可单独轮换与撤销。查找顺序：先查库，再查配置。`auth.mode=off` 且配置为空时 `/cluster/*` 仍放行，保持现有部署可用。

### D7：三级灰度，默认不改变现有行为

```json
"auth": { "mode": "off" }
```

| mode | 未认证请求 | 用途 |
|---|---|---|
| `off` | 全部放行（现状） | 默认值，升级即兼容 |
| `warn` | 放行，但记录 `auth_would_deny` 指标与日志 | 上线观察期，确认不会有正常流量被挡 |
| `enforce` | 按权限表拒绝 | 正式生效 |

`worker_token` 独立于 `auth.mode`：`worker_tokens` 非空时，`/cluster/*` 立即要求 token（不管 mode）。这样可以先收 worker 通道，再收用户通道。

### D8：授权在路由层，不在 handler 里散落

```rust
let jobs_write = post(submit).route_layer(require(Permission::JobSubmit));
let jobs_read  = get(list).route_layer(require(Permission::JobReadAll));
Router::new().route("/jobs", jobs_write.merge(jobs_read))
```

- 权限表在 `router()` 一处可见，评审时一眼看完。
- 需要资源归属的（`GET /jobs/{id}`、`DELETE /jobs/{id}`）在 handler 内查 `owners`，因为中间件拿不到 job_id 对应的主体。
- 新增端点必须挂 `route_layer`，CI 用一条测试保证"每个 `/jobs`、`/suites`、`/suite-runs` 路由都有 layer"（读 `Router` 不方便，改为在 `router()` 里用辅助函数强制传入权限）。

### D9：auth 数据独立库，per-row 表

不复用 `Store<ManagerData>`（单快照，会随会话/审计膨胀）。`data_dir/auth.sqlite`，普通表 + 索引：

```sql
CREATE TABLE principals(
  sub TEXT PRIMARY KEY, provider TEXT NOT NULL, login TEXT NOT NULL,
  name TEXT, email TEXT, avatar_url TEXT,
  first_seen REAL NOT NULL, last_seen REAL NOT NULL
);
CREATE INDEX principals_login ON principals(login);

CREATE TABLE sessions(
  token_sha256 TEXT PRIMARY KEY, sub TEXT NOT NULL, kind TEXT NOT NULL, -- web|cli
  created_at REAL NOT NULL, expires_at REAL NOT NULL, last_seen REAL NOT NULL,
  revoked_at REAL, user_agent TEXT, ip TEXT
);
CREATE INDEX sessions_sub ON sessions(sub);

CREATE TABLE role_cache(
  sub TEXT PRIMARY KEY, is_org_member INTEGER NOT NULL, is_early_access INTEGER NOT NULL,
  checked_at REAL NOT NULL, expires_at REAL NOT NULL
);

CREATE TABLE login_states(
  state TEXT PRIMARY KEY, kind TEXT NOT NULL, pkce_verifier TEXT,
  redirect_after TEXT, created_at REAL NOT NULL, expires_at REAL NOT NULL, consumed_at REAL
);

CREATE TABLE audit(
  id INTEGER PRIMARY KEY AUTOINCREMENT, at REAL NOT NULL, sub TEXT, login TEXT,
  action TEXT NOT NULL, target TEXT, result TEXT NOT NULL, ip TEXT, detail TEXT
);
CREATE INDEX audit_at ON audit(at);
```

`login_states` 是唯一会高频写入的表（每次登录一行），启动与每小时清理过期行。

### D10：CSRF 用 SameSite=Lax + Origin 校验

console UI 与 API 同源。`SameSite=Lax` 下跨站 `POST` 不带 cookie；再校验 `Origin`/`Referer` 的 host 等于 `public_base_url`，即可覆盖。不引入 CSRF token（多一个状态、多一处失败模式）。

例外：`Authorization: Bearer` 的 CLI 请求不校验 Origin（没有浏览器参与）。

### D11：审计独立、可查询、不含凭据

写操作（`job.submit` / `job.cancel` / `suite.publish` / `suite.run` / `session.revoke` / `worker.drain` / `login` / `login_failed`）各一行。字段只放 `sub` / `login` / `action` / `target` / `result` / `ip`。**不记录 token、不记录源码、不记录完整请求体**。

### D12：测试用 `provider.kind = "static"`

CI 不能打 GitHub。`static` provider 从配置读固定账号与团队关系：

```json
"auth": {
  "provider": {"kind": "static", "users": [
    {"login": "alice", "id": 1, "name": "Alice", "team": "earlyaccessdevelopers"},
    {"login": "bob",   "id": 2, "name": "Bob",   "team": null}
  ]}
}
```

`POST /auth/github/exchange` 在 static 模式下接受 `{access_token: "alice"}`。这比 mock HTTP 更稳（不打桩第三方，只换 provider）。

## 4. 登录流程

### 4.1 浏览器

```
GET /auth/login?redirect=/ui
  ├─ 生成 state(32B) + PKCE(S256 verifier)
  ├─ 写 login_states(state, verifier, kind=web, redirect, TTL 10min)
  ├─ Set-Cookie rvb_oauth_state=<state>; HttpOnly; Secure; SameSite=Lax; Max-Age=600
  └─ 302 https://github.com/login/oauth/authorize?client_id=…&scope=read:user read:org
        &state=…&code_challenge=…&code_challenge_method=S256&redirect_uri=…/auth/callback

GET /auth/callback?code=&state=
  ├─ query.state 必须等于 rvb_oauth_state cookie（防 login CSRF：别人发起的 code 换不进你的浏览器）
  ├─ state 必须存在、未消费、未过期 → 标记 consumed
  ├─ POST github.com/login/oauth/access_token（code + verifier + secret）→ access_token
  ├─ GET api.github.com/user → {id, login, name, email, avatar_url}
  ├─ GET api.github.com/user/teams?per_page=100 → 匹配 org.login=rvbench & slug=earlyaccessdevelopers
  │    （超过 100 个团队时翻页，最多 5 页；超过则记 warn 并按未匹配处理）
  ├─ upsert principals，写 role_cache
  ├─ 建 session（kind=web，12h），Set-Cookie rvb_session
  ├─ 清 rvb_oauth_state（Max-Age=0）
  └─ 302 到 redirect（只允许同源相对路径，防开放重定向）
```

没有 state cookie 也能挡住"猜 state"，但挡不住 login CSRF（攻击者把自己发起的 `code` 诱导受害者点开，受害者的浏览器就会登进攻击者的账号）。cookie 绑定浏览器身份，是这一层的关键。

`scope` 说明：`read:org` 是读团队关系所必需。普通用户授权时会看到"读取组织与团队信息"——内测阶段可接受。用户量上来后切 GitHub App（`members:read` installation token），不再要求用户授予 `read:org`（见 §13 R3）。

### 4.2 CLI

```
rvbench auth login
  ├─ POST https://github.com/login/device/code {client_id, scope:"read:user read:org"}
  ├─ 打印 "打开 https://github.com/login/device，输入 ABCD-1234"
  ├─ 按 interval 轮询 access_token（处理 authorization_pending / slow_down）
  ├─ POST {base}/auth/github/exchange {access_token}
  │    manager: 校验 → 查 user/teams → 建 session(kind=cli, 30d) → 返回 rvb_ token
  └─ 写 ~/.config/rvbench/credentials（0600），打印 login 与角色
```

`rvbench auth whoami` → `GET /auth/me`。`rvbench auth logout` → `POST /auth/logout` + 删本地文件。

### 4.3 请求鉴权（中间件）

```
1. 取凭据：Authorization: Bearer 优先，否则 cookie rvb_session
2. 前缀分流（两者不重叠：rvb_ 与 rvbw_）
   ├─ rvbw_… → 机器通道
   │    sha256 查 workers 表（未命中再查 worker_tokens 配置）
   │    命中 → 主体 worker:<worker_id>，roles=[worker]
   │    未命中 / revoked → anonymous（不给 401，让权限层统一处理）
   └─ rvb_…  → 用户通道
        sha256 查 sessions：不存在 / 过期 / revoked → anonymous
        取 principal + 角色：role_cache 命中？否则刷新（D3）
3. 权限不足：401（未登录）或 403（已登录无权）
4. 命中后写 last_seen（用户会话 web 剩余 <6h 则重发 cookie；worker 只更新内存中的 last_seen，不写会话表）
```

worker 请求不走 `sessions` 表：它的凭据是长期配置/记录，不是登录会话。`last_seen` 直接更新 `workers.last_seen`（每 2–3 秒一次心跳，写库频率可控；如需更低开销，可在内存里聚合、每 10 秒落一次）。

`/healthz`、`/ui`、`/metrics`、`/results`、`/leaderboard` 不建立会话，避免每个探针都写库。

## 5. 接口定义

### 5.1 端点

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| `GET` | `/auth/login` | 公开 | `?redirect=`（同源相对路径）；302 到 provider |
| `GET` | `/auth/callback` | 公开 | provider 回调；web 设 cookie，失败 302 到 `/ui?auth_error=` |
| `POST` | `/auth/github/exchange` | 公开 | CLI 用 GitHub token 换 `rvb_` token |
| `GET` | `/auth/me` | user | 主体、角色、权限、`roles_stale` |
| `POST` | `/auth/logout` | user | 撤销当前会话 |
| `GET` | `/auth/sessions` | user | 自己的会话列表（不含 token） |
| `DELETE` | `/auth/sessions/{id}` | 自己 / admin | 撤销指定会话 |
| `GET` | `/auth/audit` | admin | `?sub=&action=&since=&limit=` |
| `GET` | `/auth/config` | 公开 | 前端需要的非敏感配置：登录地址、是否启用、provider 显示名 |

`/auth/config` 让 console UI 在 `auth.mode=off` 时不显示登录按钮，避免把用户引到一个 503 的登录页。

worker 管理与认领端点（`/workers`、`/claims`、`/cluster/workers/claim`）见 §2「worker 管理端点」与「首次认领」。

### 5.3 配置

```json
{
  "listen": "100.70.103.65:18800",
  "data_dir": "/data",
  "victoriametrics": null,
  "auth": {
    "mode": "warn",
    "public_base_url": "https://rvbench.hk.c4y.dev",
    "provider": {
      "kind": "github",
      "client_id": "Iv1.0123456789abcdef",
      "client_secret_env": "RVBENCH_GITHUB_CLIENT_SECRET",
      "org": "rvbench",
      "team_slug": "earlyaccessdevelopers"
    },
    "admins": ["github:1234567"],
    "session_ttl_hours": 12,
    "cli_token_ttl_days": 30,
    "role_cache_seconds": 300,
    "allowed_redirect_hosts": ["rvbench.hk.c4y.dev"],
    "allow_insecure_cookie": false
  },
  "worker_tokens": [
    {"id": "k3-1", "sha256": "…", "created_at": "2026-10-24T00:00:00Z"}
  ]
}
```

校验规则（`Config` 仍 `deny_unknown_fields`）：

| 规则 | 违反 |
|---|---|
| `mode != off` 时必须配 `public_base_url`；scheme 必须是 https，或 http + loopback（`127.0.0.1` / `[::1]` / `localhost`） | 启动失败（防止生产误配 http） |
| `public_base_url` 是 http 且非 loopback 时，必须显式 `allow_insecure_cookie: true` | 启动失败 |
| `provider.kind = github` 时 `client_id` 与 secret 环境变量必须存在且非空 | 启动失败 |
| `client_secret_env` 指向的环境变量为空 | 启动失败（不静默降级） |
| `admins[]` 必须是 `^github:[0-9]+$` | 启动失败（不接受 login，避免改名/抢注导致的提权） |
| `worker_tokens[].sha256` 必须是 64 位小写 hex | 启动失败 |

**secret 只从环境变量读**，不进 config、不进镜像层、不进日志。`/auth/config` 不返回 `client_id`（前端不需要）。

`redirect_uri` 不单独配置，由 `public_base_url + "/auth/callback"` 拼出，并在授权请求与换 token 请求里**使用同一个值**（GitHub 会在换 token 时再次比对）。

`allow_insecure_cookie` 只影响 cookie 的 `Secure` 标志。loopback http 自动视为 true（不必配置）；其他 http 必须显式打开。生产永远走 https，此项保持 false。

**bootstrap**：首次部署 `admins` 留空。用任意账号登录后 `GET /auth/me` 拿到自己的 `sub`，写回配置并重启。这是唯一需要重启才能生效的配置项（其余都是每请求读取）。在拿到 sub 之前，`/auth/audit` 无人可访问——这是有意的，不给"第一个登录的人自动成为 admin"的捷径。

### 5.4 本地凭据与 CLI

照搬 CNB CLI 的分层做法（`~/.cnb/token` + `CNB_TOKEN` 环境变量），因为要解决的是同一类问题：同一个人有多套环境、CI 里不能交互登录、token 过期后要能看出来。

**文件**

`~/.config/rvbench/credentials`（Windows：`%APPDATA%\rvbench\credentials`），权限 `0600`，父目录 `0700`。

```json
{
  "auths": {
    "rvbench.hk.c4y.dev": {
      "token": "rvb_…",
      "expires_at": 1794384000,
      "refresh_token": null,
      "sub": "github:1234567",
      "login": "c4y",
      "base_url": "https://rvbench.hk.c4y.dev",
      "client": "rvbench-cli/0.1.0",
      "login_at": 1791792000
    },
    "127.0.0.1:18800": {
      "token": "rvb_…",
      "expires_at": 1794384000,
      "refresh_token": null,
      "sub": "github:1",
      "login": "alice",
      "base_url": "http://127.0.0.1:18800",
      "client": "rvbench-cli/0.1.0",
      "login_at": 1791792000
    }
  },
  "workers": {
    "rvbench.hk.c4y.dev": {
      "worker_id": "k3-1",
      "token": "rvbw_…",
      "expires_at": null,
      "visibility": "public",
      "owner": "org:rvbench",
      "login_at": 1791792000
    }
  }
}
```

三个结构上的决定，都是从 CNB 抄的：

| 决定 | 理由 |
|---|---|
| `auths` 按 host 分组 | 本地 manager 与生产 manager 各有 token，`--base` 自动选中对应条目。单 token 文件在切换环境时会拿错凭据 |
| `expires_at` 存文件 | CLI 能在本地判断过期并提示重新登录，不用等一次 401 |
| `refresh_token` 字段先留空 | v1 签 30 天固定 token，不做刷新；字段留位，v1.1 换成 7 天 access + 90 天 refresh 时不必改文件格式 |

`workers` 单独成段：worker 命令（`worker status`、`worker logout`、板上 `worker login`）只读这一段，用户命令只读 `auths`。两套凭据不会互相覆盖。

**优先级**（高到低）

| 来源 | 用途 | 示例 |
|---|---|---|
| `RVBENCH_TOKEN` / `RVBENCH_WORKER_TOKEN` | CI、容器、临时覆盖 | `RVBENCH_TOKEN=rvb_… rvbench job submit` |
| 凭据文件对应段 | 交互式登录的产物 | `auths[host]` / `workers[host]` |
| `--token` 命令行参数 | 一次性调试 | 不进 shell history（建议用 env） |
| worker 的 `config.manager_token` | 兜底（不推荐，明文进配置/镜像） | systemd `EnvironmentFile` 更合适 |

环境变量最高，是因为 CI 里没有文件、也不该有文件；配置文件放最后，是因为它最容易进版本库和镜像层。

**CLI 行为**

```sh
rvbench auth login                 # 人：device flow → 写 auths[host]
rvbench auth status                # 主体、角色、token 前缀、过期时间、来源（env/file）
rvbench auth logout                # 撤销服务端会话 + 删本地段

rvbench worker login --base …      # 机器：claim 流程 → 写 workers[host]，0600
rvbench worker status              # worker_id、owner、visibility、token 前缀、最近心跳
rvbench worker logout              # 撤销 worker token（调 DELETE /workers/{id} 需 owner，或只删本地）
```

`auth status` 输出示例（不打印完整 token）：

```
host          https://rvbench.hk.c4y.dev
user          c4y (github:1234567)
roles         user, early_access
user token    rvb_9f2c…   expires 2026-11-23 (30d)
token source  file
worker        k3-1 (public, org:rvbench)
worker token  rvbw_7f3c…  no expiry
```

**过期与刷新**

| 凭据 | v1 | v1.1 |
|---|---|---|
| 用户 token `rvb_` | 30 天固定；过期即 401，重新 `auth login` | 7 天 access + 90 天 refresh，CLI 在剩余 <1 天时自动刷新 |
| worker token `rvbw_` | 默认不过期，靠撤销与轮换控制 | 可配 `worker_token_ttl_days`；到期前 worker 用旧 token 自助续期 |

v1 不做 refresh 的原因：`rvb_` 权限只有提交任务与读自己的结果，30 天窗口可接受；而 refresh 需要多一张表、一个端点、CLI 的并发刷新锁（同一 refresh token 被两个进程同时用会互相作废），收益不如先把主链路跑通。

**文件安全**

| 项 | 做法 |
|---|---|
| 权限 | 文件 `0600`、目录 `0700`；Windows 依赖 ACL（不做额外处理，文档说明） |
| 写入 | 临时文件 + `rename` 原子替换；不要先清空再写 |
| 打印 | 所有命令只输出 token 前 8 位（`rvb_9f2c…`），`status` 也不给全量 |
| 环境变量 | 不写入日志；manager 侧对 `Authorization` 头整体脱敏 |
| 泄漏处置 | `auth logout` 撤销会话；`worker logout` 撤销 worker 记录；两者都在服务端立即生效 |

**与 CNB 的差异**（哪些抄了、哪些没抄）

| 维度 | CNB CLI | 本设计 | 为什么 |
|---|---|---|---|
| 人的登录 | `cnb login`，OAuth2 device flow | `rvbench auth login`，同一套 device flow | 抄 |
| 机器的登录 | 没有专门流程，CI 直接给 `CNB_TOKEN` | claim：worker 发起、人在网页确认 | 加。机器不该让人手工搬一个长期密钥 |
| 凭据文件 | `~/.cnb/token`，`auths.<host>` | 同结构，多一个 `workers.<host>` 段 | 抄结构，按"人/机器"分段 |
| 优先级 | `CNB_TOKEN` > 文件 | 同 | 抄 |
| 过期 | access 短效 + refresh 自动刷新 | v1 固定 30 天，refresh 字段留位 | 不抄。v1 权限小、用户少，刷新的表/端点/并发锁成本高于收益 |
| 撤销 | `cnb logout` | `auth logout` / `worker logout`，服务端即时失效 | 抄，并补 worker 自撤销 |

### 5.5 错误码

| code | HTTP | 场景 |
|---|---|---|
| `unauthenticated` | 401 | 无凭据或会话失效；带 `WWW-Authenticate: Bearer` |
| `forbidden` | 403 | 已登录但缺权限；`details.required` 给权限名 |
| `auth_disabled` | 503 | `mode=off` 时访问 `/auth/login` |
| `provider_unavailable` | 502 | 登录时 GitHub 不可达（不影响已登录用户） |
| `state_invalid` | 400 | state 缺失/过期/已消费 |
| `grant_invalid` | 401 | 换 token 失败（GitHub 拒绝） |
| `redirect_not_allowed` | 400 | `redirect` 不是同源相对路径 |
| `rate_limited` | 429 | 登录/换 token 频率超限 |

## 6. 安全

| 威胁 | 对策 |
|---|---|
| token 泄漏 | 只存 sha256；cookie `HttpOnly`；URL 从不携带 token；日志脱敏 `rvb_[A-Za-z0-9_-]+` |
| 会话固定 / 重放 | 登录后新签发（不复用任何客户端提供的 id）；state 一次性且 10min 过期 |
| CSRF | `SameSite=Lax` + `Origin` 校验（D10） |
| 开放重定向 | `redirect` 只接受 `^/[^/]` 开头的相对路径，且 host 必须在白名单 |
| 角色提升 | 角色只由 provider 数据派生；客户端字段一律忽略；`admins` 只读配置且按 `sub` 匹配 |
| 假 worker | `worker` 角色 + 每台一份 token（D6）；token 的 `id` 必须等于注册的 `worker_id`；`visibility` 由记录决定、worker 不能自封 public；`worker_tokens` 为空时记录告警但不阻断（灰度期） |
| 私有 worker 被他人占用 | `allocate()` 按 `owners[job]` 过滤：private worker 只接 owner 的 job；`owners` 缺失的历史 job 只去 public |
| 全部 worker 变私有导致公共 job 饿死 | 至少保留一台 `visibility=public`（admin 管理）；`GET /workers?visibility=public` 为空时在 `/healthz` 与 console 告警 |
| 暴力破解登录 | `/auth/login`、`/auth/github/exchange` 按 IP 限流（10/min，令牌桶，内存） |
| GitHub 不可用 | 降级 `user` + `roles_stale`（D3），不 fail-open |
| 审计被篡改 | 只追加；`DELETE /auth/audit` 不存在；轮转靠外部备份 |
| 源码/结果泄漏 | `job:read:self` 按 owner 校验；`/results` 只暴露聚合，不含 source |

未覆盖（已知缺口）：无 MFA（依赖 GitHub）、无 IP 白名单、无 SSO 强制、无细粒度资源 ACL（只有 owner/admin 两档）。

## 8. OAuth App 注册与本地开发

### 8.1 一个 App 还是两个

2026-08-14 起 GitHub 允许 **OAuth App 登记最多 10 个 redirect URI**（此前只有一个）。所以两种做法都成立：

| 方案 | 凭据 | 隔离性 | 适用 |
|---|---|---|---|
| 一个 App + 多个 redirect URI | 一套 client_id/secret | 差：生产 secret 必须出现在开发机上 | 开发机完全可信、只有一个人 |
| 两个 App（`rvbench` / `rvbench-dev`） | 两套 | 好：生产 secret 只在集群 | **本设计采用** |

推荐两个，不是因为多 URI 不可用，而是因为**生产的 `client_secret` 不该躺在开发机上**。多 URI 能力更适合「生产 + 预发」这类同一信任级别的环境；生产与开发机是两个信任级别。

两个 App 的额外好处：dev App 可以随时删掉重建不影响线上；两边的 scope 可以不同（dev 甚至可以先只给 `read:user`，团队关系用 static provider 覆盖）。

### 8.2 注册参数

| 项 | 生产 `rvbench` | 开发 `rvbench-dev` |
|---|---|---|
| 归属 | rvbench 组织 | 个人账号（或组织） |
| Homepage URL | `https://rvbench.hk.c4y.dev` | `http://127.0.0.1:18800` |
| Authorization callback URL | `https://rvbench.hk.c4y.dev/auth/callback` | `http://127.0.0.1:18800/auth/callback` |
| Enable Device Flow | ✓ | ✓ |
| **Wildcard matching** | **必须关闭** | **必须关闭** |
| Expire user access tokens | 保持默认（开） | 保持默认（开） |

几个容易踩的点：

1. **wildcard matching 要逐个确认关闭**。关闭时 redirect URL 必须与登记值**逐字符相等**；开启时 host（不含子域）与 port 必须相同、path 必须是登记值的子目录，而且**任意子域**都算匹配——`https://evil.rvbench.hk.c4y.dev/auth/callback` 也会拿到 code。2026-08-03 之前创建的单 URI App 默认开启，新建的也要点进去看一眼。
2. **loopback 的端口豁免**。GitHub 规定 loopback 的 `redirect_uri` 不需要匹配登记时写的端口：登记 `http://127.0.0.1/auth/callback` 后，`http://127.0.0.1:18800/auth/callback` 也合法。想省事就这么登记；想更严就写死端口。本设计写死 `:18800`，因为 manager 端口固定。
3. **换 token 时要带同一个 `redirect_uri`**。GitHub 在第二步会再比对一次，授权时用什么、换 token 时就得用什么。
4. **组织可能限制第三方 OAuth App**。rvbench 组织如果开了 third-party access 限制，成员授权 `rvbench` 会被 block。到 `Organization settings → Third-party access` 确认该 App 是 allowed，或临时移除限制。
5. **不要申请 `offline_access`**。新建 OAuth App 默认签发 8 小时短效 token；我们拿到后立即调 `/user` 与 `/user/teams` 并换成 `rvb_` token，不存 GitHub token，所以短效与否都不影响。申请 refresh token 只会多一份需要保管的秘密。

### 8.3 为什么不用 rvbench.internal / rvbench.test

`.internal` 是 ICANN 保留的私有 TLD，`.test` 是 RFC 2606 保留的测试 TLD，两者都不在公网 DNS 里，必须改 hosts。能用，但不建议作为默认：

| 对比 | `http://127.0.0.1:18800` | `http://rvbench.test:18800` |
|---|---|---|
| hosts / DNS | 不需要 | 需要 `127.0.0.1 rvbench.test` |
| secure context | 是（Chrome/Firefox 视 loopback 为可信源），`Secure` cookie 可写入 | 否，必须关掉 cookie 的 `Secure` |
| GitHub 建议 | 明确推荐 loopback literal | 未提及 |
| cookie 隔离 | 与生产天然不同 host | 同左 |

结论：本地用 `127.0.0.1`。真要测「不同子域共享 cookie」这类行为，再加 `rvbench.test` + `allow_insecure_cookie: true`，但别把它当成默认开发地址。

### 8.4 更好的开发方式：日常用 static provider

绝大多数开发根本不需要走 GitHub：

```json
{
  "auth": {
    "mode": "enforce",
    "provider": {
      "kind": "static",
      "users": [
        {"login": "alice", "id": 1, "name": "Alice", "team": "earlyaccessdevelopers"},
        {"login": "bob", "id": 2, "name": "Bob", "team": null}
      ]
    }
  }
}
```

```sh
rvbench --base http://127.0.0.1:18800 auth login --static alice   # EAD
rvbench --base http://127.0.0.1:18800 auth login --static bob     # 普通用户
```

好处：离线可跑、不用管 OAuth 回调、一条命令切角色（验证 401/403 边界）、CI 用同一套。**只有联调真实授权流程时才切到 `kind: github` + dev App**——那种场景是验 scope 提示、team 匹配、token 交换，一周跑不了几次。

### 8.5 环境矩阵

| 环境 | provider | App | `public_base_url` | cookie `Secure` |
|---|---|---|---|---|
| 本地日常 | `static` | 无 | `http://127.0.0.1:18800` | 自动 false |
| 本地联调 | `github` | `rvbench-dev` | `http://127.0.0.1:18800` | 自动 false |
| 预发（如有） | `github` | `rvbench-dev` | `https://staging.rvbench.hk.c4y.dev` | true |
| 生产 | `github` | `rvbench` | `https://rvbench.hk.c4y.dev` | true |

预发复用 dev App 时，在 dev App 里加第二条 redirect URI 即可——这正是多 URI 能力合适的场景（同一信任级别）。

### 8.6 secret 注入

| 环境 | 方式 |
|---|---|
| 生产（k3s） | `kubectl -n rvbench create secret generic rvbench-auth --from-literal=github-client-secret=…`，Deployment `envFrom: secretRef` |
| 本地 | `.env`（gitignore）或 `export RVBENCH_GITHUB_DEV_CLIENT_SECRET=…` |
| CI | 只在 static provider 下跑，不需要 secret |

`client_secret_env` 让两个 App 可以共用一个 manager 二进制、只换环境变量名。secret 不进 `config.json`、不进镜像层、不进日志——启动时只打印 `provider=github client_id=…（末尾 4 位）`。

## 9. 发布与灰度

| 步 | 动作 | 验证 |
|---|---|---|
| 1a | 建生产 OAuth App `rvbench`（回调 `https://rvbench.hk.c4y.dev/auth/callback`，勾选 Enable Device Flow，**关闭 wildcard**） | `client_id` 可用；用授权页实测一次拿到 code |

| 3b | 用一个普通账号 `POST /workers {visibility: private}`，把返回的 `rvbw_` 配到一块测试板 | 该 worker 只出现给 owner 与 admin；owner 的 job 能调度上去，别人的 job 不会 |
| 4 | `auth.mode=warn`，`/auth/*` 可用 | `auth_would_deny` 应为 0（除预期的匿名写请求） |
| 5 | 观察 3 天，确认无正常流量被误判 | 指标 + 抽样日志 |
| 6 | `auth.mode=enforce` | 匿名 `POST /jobs` → 401；`alice`（EAD）→ `suite:publish` 允许 |
| 7 | console UI 加登录入口 | 未登录显示"登录"，登录后显示 login 与角色 |

回滚：`mode` 改回 `off` 立即生效（配置热加载不做，重启 manager；或提供 `PUT /auth/mode` 给 admin，风险更高，v1 不做）。

| 层 | 用例 |
|---|---|
| provider | `static` provider 覆盖 4 种角色；`github` adapter 用本地 axum mock（authorize/exchange/user/teams 四个端点），断言 scope、PKCE、错误分支 |
| session | token 生成唯一、哈希稳定；过期/撤销/续期边界；`last_seen` 滑动不写穿 |
| role | 缓存命中/过期/降级三条路径；GitHub 500 时 suite 权限被收回、job 权限保留 |
| 中间件 | 每个业务路由都有 layer（表驱动断言）；`mode=off/warn/enforce` 三态矩阵 |
| 路由 | 匿名 401；`user` 打 `POST /suites` → 403；`early_access` → 201；owner 不匹配 → 404（不是 403，避免枚举） |

| worker 归属 | private worker 只接 owner 的 job（另一账号提交的 job 不分配给它）；`owners` 缺失的历史 job 只去 public；删除有在途 assignment → 409；轮换后旧 token 立即 401 |

## 11. 风险与未决

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| R1 | `read:org` 对普通用户是敏感 scope，可能劝退 | 登录转化率 | 内测期接受；用户量上来切 GitHub App（`members:read`） |
| R2 | GitHub 不可用 | 登录中断 | 降级 `user`；已登录会话不受影响（角色缓存 5min，之后降级但不断线） |
| R3 | 团队 slug 与实际不符 | EAD 判定永远为空 | 用 `GET /orgs/rvbench/teams` 核对一次，配置写死 slug；启动时打印解析结果 |
| R4 | 单快照 + 独立 auth 库两套存储 | 一致性心智负担 | 明确边界：auth 只存身份/会话/审计；业务归属（`owners`）在 `ManagerData`，与 job 同事务 |
| R5 | `auth.mode=warn` 期间仍有真实风险 | 假 worker 可注册 | 第 3 步先收 worker 通道，用户通道后收；warn 期只观察 3 天 |
| R6 | console UI 是协议仓内嵌 HTML | 改 UI 要动协议仓并升 rev | 登录态只加很小的顶部栏 + `fetch` 默认带 cookie（同源自动带）；不引入前端框架 |
| R7 | 无速率限制基础设施 | 登录端点可被刷 | 进程内令牌桶（按 IP），单实例够用；多实例时上移 Traefik rateLimit |
| R8 | 用户自建 private worker 后不跑任务 | 板子空转且占配额 | `GET /workers` 显示 `last_seen`；90 天无心跳的 `pending` 记录可清理（不自动删 active） |
| R9 | claim 端点无凭据，可被刷或抢注 worker_id | 占用待确认名额、干扰上架 | 限流（IP 5/min、全局 20 待确认）、code 10 分钟、确认页展示来源 IP 供核对；被抢注时 admin 删除 pending 记录或换 id |
| R10 | 用户在确认页误点 | 板子绑错人 | 确认页展示 worker_id 与来源 IP；owner 可转交（admin 改 owner）留作 v1.1 |
| R11 | 凭据文件被复制或误提交 | token 泄漏 | `0600` + 原子写 + 只打印前缀；文档提示 `.gitignore`；`auth logout` / `worker logout` 服务端即时失效 |
| R12 | Windows 上的文件权限不受 `0600` 约束 | 同机其他用户可读 | 已声明为已知缺口；敏感场景改用 `RVBENCH_TOKEN` 环境变量（进程级），并在 v1.1 尝试 ACL |

**待评审拍板**

1. GitHub OAuth App（v1，快）还是 GitHub App（规范，但要多管私钥与安装）。现选前者，App 作为 v1.1。
2. `early_access` 是否要求"org 成员 + team 成员"两个条件。现设计只看 team（team 成员必然是 org 成员）。
3. 是否允许匿名看 `/results` 与 `/leaderboard`。现设计允许（公开榜单是展示价值），但会暴露 case 名与 worker 拓扑的聚合。
4. `worker_token` 是单一共享密钥还是每 worker 一份。现设计每 worker 一份（可单独撤销），配置略长。

## 12. 与 suites 的衔接

自定义 suite 的 spec 里有 6 处需要按本文修订（P2 开工时一并改）：

| suites 文档位置 | 现状 | 改为 |
|---|---|---|
| §3 D10 | `admin_token` + 未配置则 503 | 删除；`POST/PUT/DELETE /suites*` 要求 `suite:publish`，`POST /suite-runs` 要求 `suite:run` |
| §6.1 `POST /suites` | body 含 `suite_id`（含 owner） | body 只有 `{name, title}`；owner 从 `sub` 派生；`suite_id = <login>/<name>` |
| §6.2 `SuiteVersionDetail.created_by` | `string` | `{sub, login}` |
| §6.2 `SuiteRun` | 无 owner | 新增 `owner: {sub, login}` |
| §6.2 `SuiteRunRequest` / 配额 D11 | 按自报 owner 计 | 按 `sub` 计（`4` 个未完成 run、`256 MiB`） |
| §6.1 读端点 | 公开 | `GET /suites*`、`GET /suite-runs/{id}` 要求登录；非 owner 返回 404（不是 403） |

另外两条不写在表里但很重要：

- suite 包仍然可以在 worker 上执行任意 Python。**身份 ≠ 沙箱**，`allow_user_suites` 默认关闭这条不变。
- CLI 的 `suite push/run` 会自动带 token；未登录时提示 `rvbench auth login`，而不是抛 401。

## 13. 为什么这个顺序更好（结论复述）

1. **归属先于资源**。suites 一旦发布就带 owner；owner 从自报改成派生是破坏性变更，需要迁移已发布的 suite。先有身份，suites 一次做对。
2. **配额先于配额对象**。没有稳定主体，配额只是装饰。
3. **worker 认证与身份解耦**。P0 可以先做，不阻塞在 GitHub App 审批/配置上。
4. **删掉临时方案**。suites 草案里的 `admin_token` 不用实现，少一条将来要拆的代码路径。
