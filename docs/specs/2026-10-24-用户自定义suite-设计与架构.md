# 用户自定义 suite：功能设计与软件架构

状态：**草案（待评审）** ｜ 涉及六个仓 ｜ 协议目标版本 `1.1.0` ｜ spec 兼容 `2.0.0` / `2.1.0`

实施顺序：**P2**，依赖 [用户身份与权限](2026-10-24-用户身份与权限-设计与架构.md)（P0 worker token / P1 GitHub 登录）先落地。§13 列出本文需要按其修订的 6 处；D10 的 `admin_token` 不再实施。

本文定义「用户把自己的评测集（suite）提交到 manager，由集群执行并回收结构化结果」的完整设计：领域模型、协议、存储、安全、各仓改动与发布顺序。接口草案见 [contracts/api/proposals/2026-10-24-user-suites.openapi.yaml](../../contracts/api/proposals/2026-10-24-user-suites.openapi.yaml)。

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| suite 是什么 | **不可变、内容寻址的版本化资源**，不是 job 的附属字段。`(suite_id, version)` 一经发布不可修改，改就是新版本。 |
| 谁展开 case | **manager 展开**成 case 级 job。复用现有租约、重试、容量、幂等，单 case 失败互不污染。 |
| worker 怎么拿到 case | **内联在 `JobRequest.case_spec`**，assignment 自包含。v1 不依赖 worker 回拉包。 |
| worker 怎么执行 | 新增**通用 case runner**（`adapters/suite_case.py`），由 `case_spec` 驱动构造输入、绑定参数、比对输出。现有 14 算子硬编码路径不动。 |
| 结果怎么回收 | 新增 `SuiteRun` 资源聚合子 job，`GET /suite-runs/{id}` 给进度与逐 case 判定。 |
| 谁能上传 | 需要 admin token；**未配置 token 时上传端点整体 503**（不是放开）。worker 另需显式 `allow_user_suites=true` 才接这类 job。 |
| 官方 suite 怎么办 | 走同一条路径：`rvbench suite pack suites/kernels/nano` 上传即可。manager 可配 `seed_suites` 启动时导入。 |

## 1. 现状与要解决的问题

当前已具备：

- suite 定义（`spec.json`）有结构（`contracts/schemas/spec.schema.json`）、语义校验器（`rvbench-cli/src/spec.rs::validate_spec`）、摘要与 baseline 绑定（`rvbench-cli/src/baseline.rs`）。
- manager / worker 有完整的 job 生命周期：`JobRequest` → 租约 → 执行 → 终态事件 → 结果。
- worker 能按 `op/shape/dtype/seed` 执行 14 个 Triton 算子与 2 个 native C 算子。

缺口在于**三处断链**：

| 断点 | 现状 | 后果 |
|---|---|---|
| 定义进不了集群 | suite 只是仓库文件，wire 上没有 suite 概念 | 用户想跑自己的 suite 只能自己搭 worker、自己写脚本 |
| case 表达力不够 | `JobRequest` 只有单输入、单输出、无条件属性、无 generator 语义 | spec 里的 `attrs`、多输入、`layout.strides`、`baseline` 全部丢失 |
| 结果不成套 | 每个 job 独立，无 run 维度 | 无法回答「这套 suite 过了几个 case」 |

## 2. 目标与非目标

**目标**

1. 一条命令把本地 suite 目录发布成集群可执行的版本。
2. 一条命令提交 run，拿到逐 case 判定 + 汇总，可导出。
3. 官方 suite 与用户 suite 走同一路径、同一校验、同一执行器。
4. 上传即校验：能被集群执行的东西，在上传时就确定，不留到运行时才发现。

**非目标（本设计明确不做）**

| 不做 | 理由 / 去向 |
|---|---|
| 执行 suite 包内的任意 candidate/reference 模块 | 代码执行面过大。v1 candidate 只能来自 `JobRequest.source`（按算子映射）或 spec 声明的白名单符号；reference 限定 `torch.*` / `torch.nn.functional.*` / `flag_gems.*`。包内模块留 v2。 |
| 多租户隔离与细粒度权限 | 依赖 manager 认证体系（v1 全仓无认证）。v1 只有单一 admin token。 |
| `suite.kind = probe / microarch` 的 run 语义 | 它们的执行单元是「轴 × 档位」而非「算子 × case」，需要 spec 2.2.0 先落地。本设计保留 `suite.kind` 字段与展开器分派点，不实现。 |
| 把 measured 结果自动写回 official-suites | 发布 measured 记录仍是人工评审流程（`baseline-results` 校验已存在）。 |
| suite 级结果缓存去重 | 需要环境指纹可信，v1 只记录不复用。 |

## 3. 设计决策

### D1：suite 是版本化资源，身份由内容决定

`(suite_id, version)` 唯一；重复发布同内容返回 200 幂等，同版本不同内容返回 409。身份摘要：

```
suite_version_sha256 = canonical_digest({
  spec_sha256,                       // spec.json 原始字节
  files: [{path, sha256, size}],     // 除 spec.json 外的全部文件，按 path 字节序
                                     // （响应里的 files[] 含 spec.json，计算身份时排除）
  schema_version
})
```

包字节摘要 `package_sha256` 只用于传输完整性，**不进入身份**——压缩器版本变了不应该产生新版本。

### D2：manager 展开，worker 不做整包执行

对比过两条路：

| 方案 | 粒度 | 重试/超时 | 容量控制 | 跨板并行 | 结论 |
|---|---|---|---|---|---|
| worker 整包执行 | suite | 全有或全无 | 不可控 | 不支持 | 否 |
| manager 展开成 case job | case | 每 case 独立 | 复用现有 | 天然支持 | **采用** |

代价是 `JobRequest` 要携带 case 合同。数据量可控：单 case 合同 1–3 KB，512 case 的 run ≈ 1 MB，远低于 2 MiB 请求上限。

### D3：case 合同内联，v1 不做包分发

worker 执行一个 case 需要：`inputs[]`（含 generator/layout）、`attrs`、`call` 绑定、`returns`、`verification`、数值容差。

前五项在 spec 里，容量小，直接内联。容差原本是 `verification.output_checks[].contract` 指向的文件——**manager 在上传时把文件读出来、解析成 `atol/rtol` 内联进 `case_spec.tolerance`**，worker 不读文件。

于是 v1 的 worker 完全不需要访问 manager 拉包。这对 push-only worker（如 `K3-10.18.60.18`）是硬要求：它只能被 manager 主动投递，不能反向访问。

> v2 才考虑：contract 里声明包内自定义 reference 模块 → 需要 `GET /suites/{owner}/{name}/versions/{version}/package` + worker 本地缓存（LRU 1 GiB / 32 版本）。

### D4：协议 `1.1.0`，只加可选字段

`JobRequest` 新增四个可选字段（`suite` / `case_spec` / `case_id` / `case_contract_sha256`），现有字段一个不删、语义不变。旧 client 的请求逐字节不变，`request_sha256` 不变。

`WorkerRegistration.protocol_version` 的 enum 从 `["1.0.0"]` 扩到 `["1.0.0","1.1.0"]`。**旧 manager 会拒绝 1.1.0 worker**，所以必须 manager 先升级（见 §10）。

### D5：`JobRequest.op/shape/dtype/seed` 是 case 的投影，不是第二份真相

case 可以有多个输入、bool/int 张量、非连续布局，这些装不进现有扁平字段。但准入匹配（`worker_supports_request`）、排行榜分组、旧 worker 兼容都依赖它们。

处理方式：**投影 + 保留原值**。`case_spec` 是唯一真相，扁平字段按固定规则投影（§5.2 表），`case_spec.operator_id` 保留原始 id。投影规则写进契约，manager 生成、worker 校验。

### D6：dtype 扩到 spec 全量，靠能力表而不是 enum 拦截

spec 允许 `float16/bfloat16/float32/float64/int32/int64/bool`，现有 `JobRequest.dtype` 只有前两者的子集。v1 把 enum 扩到 7 种，是否可调度交给 worker 上报的 `environment.implementations.<impl>.dtypes` 决定。不支持的 case 在上传时**接受**，在 run 时标 `no_capable_worker`，而不是让用户对着一堆上传失败猜原因。

### D7：v1 只支持 `implementation = triton`

native C 的候选签名固定 `void candidate(const float*, const float*, float*, int)`，表达不了 `attrs`、多输入、多输出、bool。带 `case_spec` 的请求若声明 native-c，直接 400。这条限制在协议里写死，不留"运行时才发现"的坑。

### D8：可执行性判定矩阵前置到上传

spec 里大量 `execution.status = pending_probe`、`contract.status = pending`。这不是错误，是官方套件的正常状态。但直接跑会得到一堆"不可验证"。

| case 状态 | 上传 | 默认 run | `allow_pending: true` |
|---|---|---|---|
| `execution.status=ready` + `exact_values` | 接受 | 执行，可判 passed | 同左 |
| `execution.status=ready` + `allclose` + `tolerance` 已解析 | 接受 | 执行，可判 passed | 同左 |
| `allclose` 但 contract 为 `pending` | 接受 | **`skipped`**（`skip_reason=tolerance_pending`） | 执行，结果只能是 `unverifiable` |
| `execution.status=pending_probe` | 接受 | **skip** | 执行，结果 `unverifiable` |
| `method ∈ {topk_values, topk_indices, pending}` | 接受 | skip | 仍 skip（v1 runner 不支持） |
| `semantic_rules` 非空 | 接受 | skip | 仍 skip（v1 不实现规则引擎） |

矩阵写进上传响应：`SuiteVersion.cases[].runnable_in_v1`。

实测（2026-10-24，`rvbench-official-suites`）：`hello-world` 1/1 可跑；`nano` 8 个 case 全部 `pending_probe`，`softmax/mm/mv/conv2d` 的容差也仍是 `pending`，默认 run 会全部 skip。若不做这个前置判定，用户上传官方套件后会得到一次"成功但什么都没测"的 run。

### D9：包用确定性 tar.gz，安全解包

格式：`application/gzip`，根目录直接放 `spec.json` 与其余文件，不套一层目录。

确定性要求（否则同一内容两次打包摘要不同）：条目按路径字节排序；`mtime=0`；`uid=gid=0`；`uname=gname=""`；mode 归一化为 `0644`（文件）/`0755`（有执行位）。gzip 头不写文件名与 mtime。

安全解包（manager 侧，任一违反即 422）：

| 检查 | 阈值 |
|---|---|
| 条目数 | ≤ 512 |
| 单文件解压后 | ≤ 4 MiB |
| 总解压 | ≤ 32 MiB |
| 包体 | ≤ 16 MiB |
| 路径 | 必须相对、POSIX 分隔、无 `.`/`..`/盘符/反斜线/NUL；解析后仍在根内 |
| 条目类型 | 仅普通文件与目录；拒绝符号链接、硬链接、设备、FIFO |
| spec.json | 必须存在、≤ 1 MiB、UTF-8、JSON 对象 |

### D10：上传必须带 admin token；执行必须显式开启

> **已被取代（2026-10-24）**：`admin_token` 不再实施。用户体系先落地，上传/运行改由 `suite:publish` / `suite:run` 权限判定，owner 从 `sub` 派生。以 [用户身份与权限](2026-10-24-用户身份与权限-设计与架构.md) 为准，本文 §13 列出需要改动的 6 处。下面保留原始设计仅作决策留档。

manager 新增配置 `admin_token: string | null`：

- `null`（默认）→ `POST/PUT/DELETE /suites*`、`POST /suite-runs` 返回 `503 suite_api_disabled`。读端点照常。
- 配置后 → 上述端点要求 `Authorization: Bearer <token>`，不匹配返回 401。**不引入用户体系**，token 即管理员。
- 现有 job 端点与 worker 端点不要求 token（保持 v1 无认证现状，避免打断在役 worker）。

worker 新增配置 `allow_user_suites: bool = false`：

- `false` → 含 `case_spec` 的请求在 `admit` 阶段 400 `user_suites_disabled`；注册上报 `environment.suite_case=false`，manager 不会派这类 job 给它。
- `true` → 接收，并在 `capabilities` 里上报 `suite_case=true`。

理由：suite 是**会执行代码**的输入。在无认证的 manager 上放开上传等于给任意人一个板端代码执行入口。

### D11：配额与背压前置

| 配额 | 值 | 触发行为 |
|---|---|---|
| 单 suite 版本数 | 32 | 409 |
| 单版本 case 数 | 512 | 422 |
| 单次 run 展开 job 数 | 512 | 422（不部分展开） |
| 每 owner 未完成 run | 4 | 429 |
| suite 存储总量 | 256 MiB | 507 |

现有全局未完成任务上限 1000 保留。展开是单事务：要么全插，要么全不插，不产生半成品 run。

### D12：SQLite 只存元数据，包走文件系统

现有 `ManagerData` 是**单快照事务**（整个结构序列化进 SQLite）。suite 元数据若混进去，每次 job 状态变更都会重写整棵 suite 树。

因此：`ManagerData` 只新增 `runs: BTreeMap<String, RunRecord>`（run → 子 job 索引），suite 元数据与包文件放在 `data_dir/suites/` 下独立存储，由 `SuiteStore` 管理，启动时加载索引到内存 `Arc<RwLock<SuiteIndex>>`。

```
data_dir/
  manager.sqlite                  # jobs / workers / assignments / runs
  suites/
    index.json                    # 全部 suite 与版本元数据（≤ 1 MiB，原子写）
    <owner>/<name>/<version>/
      spec.json
      package.tar.gz
      manifest.json               # files[] + digests + upload 元数据
    .tmp/                         # 上传暂存，启动时清空
```

## 4. 领域模型

### 4.1 资源

```
Suite (owner, name, title, created_at, deleted_at?)
  └─ SuiteVersion (version, digest, spec_digest, status, cases[], files[], package)
       └─ SuiteRun (run_id, ref → SuiteVersion, kinds, backend, implementation,
                    state, progress, summary, jobs[])
            └─ Job (现有 JobRecord, 带 case_spec)
```

| 资源 | 主键 | 可变性 | 生命周期 |
|---|---|---|---|
| `Suite` | `suite_id = <owner>/<name>` | 标题可改，`suite_id` 不可改 | 软删除；有未完成 run 时拒绝 |
| `SuiteVersion` | `(suite_id, version)` | **不可变** | 随 suite 删除；版本不可单独删 |
| `SuiteRun` | `run_id = uuidv7` | 状态推进 | 与 job 同生命周期，不自动清理 |

### 4.2 状态机

**SuiteVersion**

```
uploading ──校验通过──> verified
    │
    └──任一校验失败──> rejected（保留记录与错误清单，便于 CLI 打印）
```

校验是同步的：`PUT` 返回时状态已确定，响应里只可能出现 `verified` / `rejected`。`uploading` 是内部中间态，仅为崩溃恢复时识别未完成上传（启动时清掉 `suites/.tmp/` 下的残留）。`rejected` 版本不占版本配额，但保留 24h 供排查。

**SuiteRun**

```
queued ──首个 job ack──> running ──全部终态──> completed | partial | failed
  │                                              ▲
  └────────────取消（无 job 开始）──> canceled ───┘
```

终态按下列顺序判定，第一条命中即止：

| 顺序 | 终态 | 条件 |
|---|---|---|
| 1 | `failed` | 存在 `error` 判定（job `failed`/`interrupted`），且无 `passed` |
| 2 | `partial` | `job_count == 0`（全部被矩阵 skip）；或存在 `failed`/`skipped`/`unverifiable`，且至少一个 `passed` |
| 3 | `completed` | `job_count > 0`、全部 job `done`、全部判定 `passed`、无 `skipped` |
| 4 | `failed` | 其余（全部 `unverifiable`，无 `passed`） |
| — | `canceled` | 用户取消，且无 job 进入 running |

「全部被 skip」判为 `partial` 而不是 `completed`，是为了避免「成功但什么都没测」被当成通过。

非终态期间 `blocked_reason` 表达「为什么还没动」：

| `blocked_reason` | 含义 |
|---|---|
| `no_capable_worker` | 无在线、未 drain 且 `worker_supports_request` 为真的 worker |
| `worker_capacity_full` | 有匹配 worker，但槽位被占 |
| `awaiting_dependencies` | 保留（当前无跨 case 依赖） |

**Job** 沿用现有 `queued / running / done / failed / canceled / interrupted`，不新增状态。

### 4.3 逐 case 判定

从 `JobRecord.evaluation.details` 归一化出 `CaseVerdict`（manager 聚合时计算，不新增 wire 字段）：

| `verdict` | 来源 |
|---|---|
| `passed` | `details.correct == true` 且执行了全部声明的 output check |
| `failed` | `details.correct == false` |
| `unverifiable` | job `done` 但 `correct` 缺失，或 case 被 skip（`pending_probe` / 容差未裁决 / 方法不支持） |
| `skipped` | 未提交执行（矩阵判定） |
| `error` | job `failed` / `interrupted` |

## 5. 数据流

### 5.1 上传与版本化

```
CLI                          manager                         磁盘
 │  pack（确定性 tar.gz）       │                              │
 │──PUT /suites/{o}/{n}/versions/{v}──▶                       │
 │                            ├─ 鉴权（admin token）           │
 │                            ├─ 体积/条目/路径检查            │
 │                            ├─ 解包到 suites/.tmp/<uuid>/   │
 │                            ├─ validate_spec(spec, dir)     │
 │                            ├─ 逐 case 展开 dry-run         │
 │                            ├─ 解析 tolerance 合同文件      │
 │                            ├─ 计算 digest                  │
 │                            ├─ 写 package + manifest       │
 │                            ├─ 更新 index.json（原子）      │
 │◀──201 SuiteVersion─────────┤                              │
```

失败语义：

| 情况 | 状态码 | body |
|---|---|---|
| suite 不存在且 `create=true` | 201 | 创建 suite + 版本 |
| suite 不存在且未声明创建 | 404 | `suite_not_found` |
| 同版本同 digest | 200 | 幂等返回既有版本 |
| 同版本不同 digest | 409 | `version_immutable` |
| schema/语义/文件摘要失败 | 422 | `validation_failed` + `errors[]`（最多 50 条） |
| 超过配额 | 409 / 507 | 见 D11 |

**数值容差合同（`numeric_contract` 1.0.0）**

`verification.output_checks[].contract.status == "resolved"` 时，`path` 指向的文件必须满足：

```json
{
  "$schema": "../../schemas/numeric_contract.schema.json",
  "schema_version": "1.0.0",
  "kind": "numeric",
  "atol": 0.005,
  "rtol": 0.005,
  "nan_equal": false,
  "inf_equal": true
}
```

| 字段 | 约束 | 违反后果 |
|---|---|---|
| `schema_version` | 固定 `1.0.0` | 解析失败 |
| `kind` | 固定 `numeric`；缺省视为不可解析 | 解析失败 |
| `atol` / `rtol` | `[0,1]` 内有限非负 | 解析失败 |
| `nan_equal` / `inf_equal` | 布尔 | 解析失败 |

文件缺失、`sha256` 不符、`kind` 不对、数值越界，任一发生 → 该 case 标 `tolerance_pending`，默认 run skip。上传本身仍成功：不阻断整份 spec，原因记在 `SuiteVersion.cases[].skip_reason`，不写 `errors[]`（那里只放阻断性错误）。

`exact_values` 不读合同，固定 `atol=rtol=0`。现有 `timing.contract` 是同一套「路径 + sha256」引用机制，但文件内容不同（`kind` 缺省），两者不要混用。

### 5.2 展开与调度

`POST /suite-runs` 在**单个 manager 事务**内完成：

1. 读 `SuiteVersion`，校验 `digest` 与请求一致（防止 TOCTOU）。
2. 按 `cases[]`（缺省全部）与 `kinds[]` 求笛卡尔积，过滤矩阵判定为 skip 的组合（记 `skipped`，不建 job）。
3. `job_count > 512` → 422。
4. 为每个组合构造 `JobRequest`（下表），插入 `s.jobs`，同时写 `s.runs[run_id].jobs`。
5. 返回 `SuiteRun` 快照。

**投影规则**（manager 唯一实现，worker 只校验）：

| `JobRequest` 字段 | 取值 | 边界 |
|---|---|---|
| `op` | `normalize(operator_id)`：小写 → 非 `[a-z0-9_]` 转 `_` → 去前导 `_`/数字 → 截断 48 | 结果必须匹配 `^[a-z][a-z0-9_]{0,47}$`，否则该 case 上传时就拒绝 |
| `shape` | 第一个 `kind=tensor` 输入的 `shape` | 维数 ≤ 6；无 tensor 输入或标量（`[]`）时为 `[1]` |
| `dtype` | 第一个 tensor 输入的 `dtype` | 无 tensor 输入时为 `float32` |
| `seed` | 第一个 tensor 输入的 `generator.seed` | `constant_v1` / 无 generator 时为 `0` |
| `implementation` | run 指定，默认 `triton` | 只接受 `triton`（D7） |
| `warmup` / `repetitions` | run 覆盖 > `policies.timing.contract` 的 `explicit_warmup`/`repetitions` > `5/20` | 上限 1000 |
| `timeout_secs` | run 指定，默认 300 | 1–1800 |
| `source` | **按算子**从 run 的 `sources` 取（见下）；单算子 run 可用 `source` 简写 | 缺省时不设置，worker 按 `case_spec.candidate` 导入白名单符号 |
| `suite` / `case_id` / `case_spec` | 见 §6.2 | |
| `client_request_id` | 不设置（run 内部用 `runs[run_id].jobs` 去重） | |

**candidate 来源**（一个 suite 覆盖多个算子，单一 `source` 装不下，必须按算子映射）：

| 情况 | `case_spec.candidate` | `JobRequest.source` |
|---|---|---|
| run 的 `sources[operator_id]` 命中 | `{"kind":"source"}` | 该算子的源码 |
| run 用 `source` 简写，且全部选中 case 同属一个算子 | `{"kind":"source"}` | 该源码 |
| run 未提供源码，spec 的 `candidate.kind=python_symbol` | `{"kind":"python_symbol","id":"flag_gems.abs"}` | `null` |
| run 未提供源码，spec 的 `candidate.kind=adapter` | — | 该 case 标 `runnable_in_v1=false`，`skip_reason=unsupported_candidate_adapter` |
| spec 的 `reference.kind=adapter`（如 `attention_math_v1`） | 按上表正常解析 | 该 case 标 `runnable_in_v1=false`，`skip_reason=unsupported_reference_adapter`；v1 不做参数量换算 |

`sources` 的键是 spec 的原始 `operator_id`（不是归一化后的 `op`），因为归一化可能碰撞（`_abs` 与 `abs` 都会得到 `abs`）。上传时检测归一化碰撞并拒绝整份 spec，避免同一 `op` 对应两份源码。

**`case_spec` 形状**（内联进 `JobRequest`，是 worker 的唯一执行依据）：

```json
{
  "case_id": "nano.abs.C01",
  "operator_id": "abs",
  "suite": {"suite_id": "rvbench/nano", "version": "0.3.1", "digest": "9f2c…"},
  "target": {"architecture": "riscv64", "backend": "spacemit", "device": "SpaceMiT K3"},
  "call": {
    "args": [{"kind": "input", "name": "x"}],
    "kwargs": {}
  },
  "returns": {"kind": "tensor", "names": ["out"]},
  "inputs": [{
    "name": "x", "kind": "tensor", "shape": [1024, 1024], "dtype": "float32",
    "layout": {"kind": "contiguous", "axes": ["row", "column"]},
    "generator": {"kind": "torch_cpu_uniform_v1", "seed": 0, "low": -10, "high": 10}
  }],
  "attrs": {},
  "outputs": [{
    "name": "out", "kind": "tensor", "shape": [1024, 1024], "dtype": "float32",
    "layout": {"kind": "contiguous", "axes": ["row", "column"]}
  }],
  "verification": {
    "output_checks": [{"output": "out", "method": "exact_values", "contract": null, "reason": null}],
    "semantic_rules": []
  },
  "tolerance": {"atol": 0.0, "rtol": 0.0, "nan_equal": false, "inf_equal": true},
  "candidate": {"kind": "source"},
  "reference": {"kind": "python_symbol", "id": "torch.abs"},
  "case_contract_sha256": "3a7d…"
}
```

字段约束：

| 字段 | 约束 |
|---|---|
| `case_id` / `operator_id` | 非空；`case_id` 在版本内唯一 |
| `suite` | 与 `JobRequest.suite` 逐字段相同 |
| `target` | 从 `suite.target` 复制；worker 用它做本地准入兜底 |
| `call.args` / `call.kwargs` | 引用 `inputs[].name` 或 `attrs` 的键；不得悬空 |
| `returns.kind` | `tensor`（单输出）或 `tuple`（多输出，顺序与 `outputs[]` 对应） |
| `inputs[]` | 1–8 个；`tensor` 或 `none`；tensor 的元素数 ≤ 16 777 216，总数 ≤ 67 108 864 |
| `attrs` | 标量或标量数组，深度 ≤ 2，≤ 32 个键 |
| `outputs[]` | 1–8 个；`tensor` 或 `pending` |
| `verification.output_checks[]` | 1–8 条，`output` 必须在 `outputs[].name` 中 |
| `tolerance` | `exact_values` 时为 `atol=0,rtol=0`；`allclose` 时必须由 resolved contract 解析得到，否则该 case 标 skipped、不建 job（上传本身仍成功） |
| `candidate` | `{"kind":"source"}` / `{"kind":"python_symbol","id":…}` / `{"kind":"adapter","id":…}`；`python_symbol` 的 `id` 白名单同 `reference`；`adapter` 的 case 不可执行 |
| `reference` | 同上；`adapter`（如 `attention_math_v1`）可上传但该 case 不可执行 |
| `case_contract_sha256` | `digest({case, operator:{id,call,returns}, target:suite.target, policies})`，与 baseline 的算法一致 |

### 5.3 执行：worker 通用 case runner

`Backend::prepare` 按 `request.case_spec.is_some()` 分派：

| 条件 | 路径 |
|---|---|
| `case_spec` 为 `None` | 现有硬编码 harness（`adapters/triton.py` / `adapters/native.c`），行为逐字节不变 |
| `case_spec` 为 `Some` 且 `implementation=triton` | `adapters/suite_case.py` |
| `case_spec` 为 `Some` 且其他实现 | `prepare` 阶段 400（D7） |

`suite_case.py` 的执行流程：

1. **构造输入**：按 `inputs[]` 顺序，`kind=tensor` 的用 generator 生成：
   | generator | 生成方式 |
   |---|---|
   | `torch_cpu_uniform_v1` | 以独立 `torch.Generator().manual_seed(seed)` 生成 float32 `[0,1)`，线性映射到 `[low,high)`，最后 `.to(dtype)`；先 float32 再 cast，避免半精度采样差异 |
   | `constant_v1` | `torch.full(shape, value, dtype)` |
   | `bernoulli_v1`（v2） | `torch.rand(...) < p` |
   | `uniform_index_v1`（v2） | `torch.randint(low, high, shape)` |
   | `sequence_v1`（v2） | `arange` 后取模 |
   
   布局：`contiguous` 直接生成；`strided` 先按 `strides` 分配底层存储再用 `as_strided(shape, strides, storage_offset)`。**基准数据按逻辑顺序生成**（先连续张量，再 `as_strided` 视图），保证不同布局下逻辑值一致。
   
2. **绑定参数**：`call.args` 按顺序逐个取 `inputs[name]` 或 `attrs[name]`；`call.kwargs` 的键是调用参数名，值取 `attrs[binding.name]`。`none` 输入传 `None`。只传 `call` 声明的参数，不额外追加 `attrs` 里未绑定的键。
3. **调用 candidate**：`candidate(*args, **kwargs)`。candidate 来源：`candidate.py`（用户 source）优先，否则按 `case_spec.candidate.id` 导入。
4. **调用 reference**：白名单 import，使用与 candidate 相同的 `args`/`kwargs` 调用。
5. **比对**：按 `returns.kind` 摊平为列表，逐 `outputs[]` 比对：
   - `exact_values`：整数/bool 用 `torch.equal`；浮点用 `torch.equal`（`-0.0` 与 `0.0` 判等，与 spec 的 note 一致）；`nan_equal=true` 时改用 `allclose(atol=0,rtol=0,equal_nan=True)`。
   - `allclose`：`|a-b| <= atol + rtol*|b|`，`NaN`/`Inf` 按 `nan_equal`/`inf_equal`。
   - `shape` 或 `dtype` 不匹配 → 该 output `failed`，不进入数值比较。
6. **计时**：沿用现有三阶段（warmup → samples → median），样本与 `preparation_excluded` 语义不变；`timing.unit` 非 `ms` 时该 case 只能 correctness（v1）。
7. **落盘**：`evaluation.json` 增加 `case_id` / `suite_digest` / `case_contract_sha256` / `verdict` / `per_output[]`，其余字段保持不变。

`verdict` 只在**该 case 确实被执行**且全部声明的 check 都通过时为 `passed`；执行了但任一 check 无法判定（方法不支持、tolerance 缺失）→ `unverifiable`。这与 spec 的 `unknown_check: not_passed` 一致。默认矩阵下这类 case 根本不建 job，记 `skipped`。

### 5.4 聚合与导出

`GET /suite-runs/{id}` 从 `runs[id].jobs` 读子 job 索引，再从 `s.jobs` 取状态，逐项计算 `verdict`：

```
summary.passed / failed / unverifiable / skipped / error
progress.queued / running / done / failed / canceled / interrupted
```

`GET /suite-runs/{id}/results` 输出 `eval_results` 1.1.0 兼容形状（`contracts/schemas/eval_results.schema.json`），每个 case 一条 `measurement`，绑定 `case_contract_sha256` 与环境指纹。这一步是**读时转换**，不落盘第二份数据。

### 6.3 `JobRequest` 扩展（协议 1.1.0）

```diff
 {
   "implementation": …, "backend": …, "kind": …, "op": …, "shape": …, "dtype": …,
   "seed": …, "warmup": …, "repetitions": …, "timeout_secs": …,
   "client_request_id": …, "source": …, "attributes": …,
+  "suite": { SuiteRef } | null,
+  "case_id": "string | null",
+  "case_spec": { CaseSpec } | null,
+  "case_contract_sha256": "sha256 | null"
 }
```

一致性规则（`validate_request` 新增）：

| 规则 | 违反 |
|---|---|
| `case_spec` 存在 ⟺ `suite` / `case_id` / `case_contract_sha256` 同时存在 | 400 |
| `case_spec.suite` 与 `suite` 逐字段相等 | 400 |
| `case_spec.case_id` 与 `case_id` 相等 | 400 |
| `implementation` 为 `triton` | 400（D7） |
| `op` / `shape` / `dtype` / `seed` 与投影规则一致 | 400（worker 侧校验；manager 生成时保证） |
| `case_spec` 的 input 元素总数 ≤ 67 108 864 | 400 |

`protocol_version`：`1.0.0`（不认识上述字段）/ `1.1.0`（认识）。worker 注册时报自己的版本；manager 只把带 `case_spec` 的 job 派给 `>= 1.1.0` 且 `environment.suite_case == true` 的 worker。

### 6.4 准入匹配

在 `worker_supports_request` 之外新增 `worker_supports_case`（协议仓，纯函数）：

```
fn worker_supports_case(worker, request) -> bool:
  if request.case_spec is None: return worker_supports_request(worker, request)
  if worker.protocol_version < 1.1.0: return false
  if worker.environment.suite_case != true: return false
  if worker_supports_request(worker, request) == false: return false
  if request.kind ∉ worker.kinds: return false
  if request.case_spec.target.architecture != worker.environment.arch: return false
  return true
```

`environment` 是 `additionalProperties: true`，所以 `arch` / `device` / `suite_case` 不需要改 schema。worker 注册时补：

```json
"environment": {
  "arch": "riscv64",
  "device": "SpacemiT K3",
  "suite_case": true,
  "implementations": {"triton": {"ready": true, "ops": [...], "dtypes": ["float16","float32"]}}
}
```

`require_target_match=true` 时的匹配分两层，不要混为一谈：

| 层 | 时机 | 比对对象 | 不匹配的结果 |
|---|---|---|---|
| suite 声明 vs 请求 | 展开时（§5.2 事务内） | `suite.target.architecture` / `backend` vs 请求的 `backend` 平台族 | 422 `unsupported_case`，整次 run 拒绝，不建 job |
| case 需求 vs 具体 worker | 每次 `allocate()` | `case_spec.target.architecture` vs `worker.environment.arch`；`op/dtype/kind/implementation` vs 能力表 | 该 job 留在队列，`blocked_reason=no_capable_worker` |

`suite.target.device` 是自由文本，只做展示与人工核对，**不参与自动匹配**——用它做准入会把「SpaceMiT K3」和「K3-1-32G」这类同物异名判成不匹配。

平台族映射（`rvbench-suite` 内的常量，非用户可配置）：

```
"spacemit" -> {k1, k3}
"riscv64"  -> {k1, k3}
```

其余 `target.backend` / `target.architecture` 一律视为与现有 backend 不兼容。

### 6.5 CLI

```sh
# 打包（确定性；同内容两次得到同一 digest）
rvbench suite pack ./my-suite -o my-suite.tar.gz

# 本地校验（不上网）
rvbench suite check my-suite.tar.gz --require-ready

# 发布（需 admin token）
rvbench --base https://rvbench.hk.c4y.dev suite push my-suite.tar.gz \
  --suite-id c4y/my-ops --version 1.0.0 --create --token "$RVBENCH_TOKEN"

# 查询
rvbench --base … suite list
rvbench --base … suite show c4y/my-ops@1.0.0

# 执行
rvbench --base … suite run c4y/my-ops@1.0.0 \
  --backend k3 --kind correctness --source my_impl.py --wait

# 取结果
rvbench --base … suite status <run-id> --wait
rvbench --base … suite results <run-id> -o results.json
```

`pack` 的确定性规则与 manager 解包校验必须共用同一实现（`rvbench-suite` crate），否则 CLI 能打包、服务端拒收。`check` 复用 `validate_spec` 与展开 dry-run，输出与 `validate spec` 相同的错误清单格式。

### 6.6 错误码

统一 `{"error": {"code": "...", "message": "...", "details": {...}}}`，沿用现有 `Error` schema 的字段语义，新增 code：

| code | HTTP | 场景 |
|---|---|---|
| `suite_api_disabled` | 503 | 未配置 admin token |
| `unauthorized` | 401 | token 缺失/错误 |
| `suite_not_found` | 404 | — |
| `version_immutable` | 409 | 同版本不同内容 |
| `digest_mismatch` | 409 | run 的 digest 与版本不符 |
| `validation_failed` | 422 | 包/spec 校验失败，`details.errors[]` |
| `package_too_large` | 413 | 超过 16 MiB |
| `quota_exceeded` | 429 / 507 | 见 D11 |
| `user_suites_disabled` | 400 | worker 未开启 |
| `unsupported_case` | 400 | 矩阵判定不可执行且 `allow_pending=false` |
| `unsupported_suite_kind` | 422 | `suite.kind != operator`（2.2.0 的 probe/microarch） |
| `run_too_large` | 422 | 展开 > 512 job |

## 7. 存储与一致性

| 数据 | 位置 | 事务边界 |
|---|---|---|
| suite 索引 | `suites/index.json` | 写临时文件 + `rename`（原子） |
| spec / 包 / manifest | `suites/<owner>/<name>/<version>/` | 先写 `.tmp/`，校验后 `rename` 目录 |
| run 与子 job 索引 | `ManagerData.runs`（随单快照写入 `manager.sqlite`） | 与 job 插入同一事务 |
| 结果 | 不另存 | 读时从 `JobRecord.evaluation.details` 计算 |

**崩溃恢复**

| 时机 | 结果 | 处理 |
|---|---|---|
| 上传写完文件、未写索引 | 孤儿目录 | 启动扫描 `suites/` 下无索引条目的目录，移入 `suites/.orphan/`，保留 24h 后清理（不直接删，索引写失败时目录本身可能是好的） |
| 索引已写、文件缺失 | 索引损坏 | 启动校验每个版本的 `manifest.json` 与文件摘要；不一致 → 版本标 `rejected` 并记 `reason` |
| 展开事务提交前崩溃 | 无 run | 事务回滚 |
| 展开事务提交后崩溃 | run 完整 | 正常恢复（`runs` 与 `jobs` 同事务） |

**为什么 run 索引进 SQLite 而不是 index.json**：run 与 job 状态必须同事务，否则会出现「run 终态但 job 还在跑」或反之。suite 元数据是只读的、变更极少，放文件更合适。

**快照体积**：`runs` 每个 run 一条记录，按 512 job × (case_id 64B + kind 16B + job_id 36B) ≈ 60 KB。10 个并发 run ≈ 600 KB，单快照可接受。超过 50 个 run 时按 `finished_at` 裁剪（保留最近 200 个）。

## 8. 安全与配额

威胁模型与对策：

| 威胁 | 对策 |
|---|---|
| 上传恶意 tar（zip slip、符号链接、超大解压） | D9 的检查表，任一违反 422；解包用 `tar::Entry::unpack_in`，不用 `unpack` |
| 上传超大包打满磁盘 | 包体 ≤ 16 MiB、总解压 ≤ 32 MiB、每 owner 256 MiB |
| 通过 suite 在板端执行任意代码 | worker `allow_user_suites=false` 默认；开启后仍走现有进程隔离 + 超时 + 进程组 kill |
| 伪造 suite 版本替换内容 | 版本不可变 + `digest` 必填 + TOCTOU 校验 |
| 单次 run 打满队列（512 × 3 kinds） | 展开上限 512 job；每 owner 4 个未完成 run；全局 1000 未完成 job |
| 容差被恶意放宽（`atol=1e9`） | 上传时校验 `atol/rtol ∈ [0, 1]`；`exact_values` 强制 `atol=rtol=0` |
| 通过 `reference` 导入任意模块 | 白名单前缀 `torch.` / `torch.nn.functional.` / `flag_gems.`；worker 侧二次校验 |
| 报告虚假 passed | 现有机制：`done` 要求 compilation/evaluation 证据 artifact 非空；verdict 由 `details.correct` 推导，manager 不信任客户端字段 |

未覆盖（明确记为已知缺口）：无用户身份、无审计日志、无速率限制、无包签名。这些依赖 manager 认证体系，v1 只做「单一 admin token + 默认关闭」的最小防线。

## 9. 仓与模块改动

### 9.1 新增 crate：`rvbench-suite`

**放在 `rvbench-core-rust` 仓内作为第二个 workspace 成员**（与 `rvbench-protocol` 同仓，分别发布 rev）。

为什么不是放进 `rvbench-protocol`：协议 crate 只该有 wire 类型与校验，加 `jsonschema` 解析与 tar 打包会让所有 client 拖上一棵解析树。为什么不是放进 CLI：manager 不能依赖 CLI（CLI 依赖 `clap`/`reqwest-blocking`/`tar`，且 bin 与 lib 混装）。

```
rvbench-suite/
  src/
    lib.rs        # pub use
    spec.rs       # validate_spec / readiness_blockers（从 cli/src/spec.rs 迁移）
    digest.rs     # canonical_digest / spec_digest / case_contract_digest
    package.rs    # 确定性 pack / 安全 unpack / manifest
    expand.rs     # SuiteVersion + run 参数 → Vec<JobRequest>（投影规则唯一实现）
    tolerance.rs  # numeric contract 解析（atol/rtol/nan_equal/inf_equal）
```

依赖：`rvbench-protocol`、`serde_json`、`jsonschema`、`sha2`、`tar`、`flate2`、`anyhow`。

**迁移策略**：先把 `cli/src/spec.rs` 的函数整体搬过去（保持逐字节相同的错误消息顺序），CLI 改为 `pub use` 转发，`tests/parity.rs` 与 `tests/commands.rs` 必须全绿后才删旧实现。

### 9.2 各仓改动清单

| 仓 | 改动 | 量级 |
|---|---|---|
| **rvbench**（主仓） | `contracts/api/openapi.json` 加 31 个 schema（14 个 `CaseSpec` 嵌套 + 17 个 suite/run 资源）；扩展 1 个（`Error.code`）；`contracts/schemas/numeric_contract.schema.json` 新增；`docs/specs/` 本文；`examples/user-suite/` 示例；`tools/sync_contract.py` 无需改 | 中 |

| **rvbench-cli** | `suite` 子命令（pack/check/push/list/show/run/status/results）；`spec.rs` 改为转发；`control.rs` 加 token 头 | 中 |

### 9.3 manager 内部结构

```
src/
  lib.rs                 # 路由装配 + Config
  suites/
    mod.rs               # SuiteStore（index.json + 文件）
    model.rs             # SuiteRecord / VersionRecord（内部类型）
    upload.rs            # 解包、校验、发布
    expand.rs            # 调用 rvbench_suite::expand
    run.rs               # RunRecord、聚合视图、取消
    error.rs             # ApiError 扩展
```

`Manager` 增加两个字段：`suites: Arc<SuiteStore>`、`admin_token: Option<String>`。路由加 `nest("/suites", suites::router())` 与 `nest("/suite-runs", run::router())`。

`Config` 扩展（仍 `deny_unknown_fields`，新字段全部可选）：

```json
{
  "listen": "0.0.0.0:18800",
  "data_dir": "/var/lib/rvbench/manager",
  "victoriametrics": null,
  "admin_token": null,
  "seed_suites": [
    {"suite_id": "rvbench/hello-world", "version": "1.0.0", "package": "/opt/rvbench/suites/hello-world.tar.gz"}
  ]
}
```

`seed_suites` 在启动时按与 `PUT` 相同的校验流程导入：版本不存在则建，已存在且 digest 相同则跳过，digest 不同则**记错误并继续**（不阻塞启动，避免一个坏包让 manager 起不来）。这是官方套件进入集群的方式，也让「官方」与「用户」共用同一条代码路径。

## 12. 风险与未决

| # | 风险 | 影响 | 处置 |
|---|---|---|---|
| R1 | 单快照事务随 run 增长 | job 事务变慢 | 已限制 512 job/run、保留 200 run；超阈值后迁移按行表（协议不变） |
| R2 | 通用 runner 与硬编码 harness 语义不一致 | 同一算子两套口径 | 带 `case_spec` 的请求强制走通用路径，禁止回落；nano 的 abs 在两条路径上做一次对拍，差异记录在测试里 |
| R3 | 官方 spec 大量 `pending_probe` / `pending` 容差 | 上传成功但跑不出结论 | D8 矩阵前置判定，`SuiteVersion.cases[].runnable_in_v1` 明确告知 |
| R4 | `op` 归一化与 spec 的 operator id 不一致（如 `_flash_attention_forward`） | 准入匹配错位 | 归一化规则写进契约；`case_spec.operator_id` 保留原值；上传时校验归一化结果合法 |
| R5 | 板端磁盘被包缓存与 job 目录吃满 | worker 失败 | v1 不缓存包（D3）；job 目录沿用现有清理策略；GC 放 v2 |
| R6 | 无认证环境下 token 泄漏 | 任意人可上传执行 | token 只经 `Authorization` 头、不进 URL/日志；未配置即关闭 |
| R7 | 2.2.0 的 probe/microarch suite 无法展开 | 用户尝试上传后 run 失败 | 上传时若 `suite.kind != "operator"` → 422 `unsupported_suite_kind`，并在消息里指向 2.2.0 路线图 |

**待评审拍板**

1. `suite_id` 是否允许 `/`（现设计 `owner/name` 两段路径）。若希望单一 id，改为 `owner.name`。
2. 是否需要「同一 candidate 跨 suite 复用结果」。需要则要引入可信环境指纹，与本设计的 `require_target_match` 有耦合。
3. `GET /suite-runs/{id}/results` 输出 `eval_results` 还是独立 `suite_results` 格式。现选前者（复用已有 schema 与校验器），代价是部分字段（`baseline_id`）为空。
4. admin token 是单值还是多值（`tokens: [{name, hash, scopes}]`）。现选单值，够用且不引入用户体系。

## 13. 与用户系统的衔接（P2 开工前必改）

用户身份与权限见 [2026-10-24-用户身份与权限-设计与架构.md](2026-10-24-用户身份与权限-设计与架构.md)。本文有 6 处要按它修订，全部是**简化**：

| 本文位置 | 现状 | 改为 |
|---|---|---|
| §3 D10 / §6.6 | `admin_token`、`suite_api_disabled` | 删除；`POST/PUT/DELETE /suites*` 要 `suite:publish`，`POST /suite-runs` 要 `suite:run` |
| §6.1 `POST /suites` | body 含 `suite_id`（带 owner） | body 只有 `{name, title}`；owner 由 `sub` 派生，`suite_id = <login>/<name>` |
| §6.2 `SuiteVersionDetail.created_by` | `string` | `{sub, login}` |
| §6.2 `SuiteRun` | 无 owner | 新增 `owner: {sub, login}` |
| §6.2 `SuiteRunRequest` / §3 D11 | 配额按自报 owner 计 | 按 `sub` 计（4 个未完成 run / 256 MiB） |
| §6.1 读端点 | 公开 | 要求登录；非 owner 返回 404（不是 403，避免枚举） |

不变的两条：

- suite 包仍会在 worker 上执行任意 Python。**身份不等于沙箱**，`allow_user_suites` 默认关闭这条保持不变。
- CLI `suite push/run` 自动带 token；未登录时提示 `rvbench auth login`，而不是抛裸 401。

顺序上的收益（为什么先做用户系统）：owner 从自报改派生是破坏性变更，先有身份才能一次做对；配额需要稳定主体；`admin_token` 不必实现，少一条将来要拆的路径。
