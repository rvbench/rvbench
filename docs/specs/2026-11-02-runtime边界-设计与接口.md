# 运行时边界：submit / runtime / worker

- 日期：2026-11-02
- 状态：提案（未实现）
- 范围：协议 `contracts/api/openapi.json`、worker 执行层、manager 调度与结果
- 配套图：`documents/架构图/05-runtime-boundary.svg`、`06-runtime-sequence.svg`（`python build_runtime_boundary.py` 生成）

## 0. 摘要

一次评测里，代码、运行时、机器是三件不同的事。本设计把它们拆成三个互不推导的维度：

1. **submit** 描述「评什么」和「用哪份代码」，不含任何机器参数与编译参数。
2. **runtime** 是一个可注册的 provider，独占「源码 → 可执行 → 一次调用 → 计时」这段，声明 ABI、工具链、能力矩阵与计时口径。
3. **worker** 是一台机器加若干执行上下文，只声明「有哪些核、怎么绑定、装了哪些 runtime」。

三条决定：

| 编号 | 决定                             | 替代方案                        | 理由             |
| -- | ------------------------------ | --------------------------- | -------------- |
| D1 | runtime 是协议一等公民，与 `backend` 正交 | 继续加 `implementation` enum 值 | 加第四个栈不用再改协议    |
| D2 | submit 可以显式选 runtime，也可以留空     | 由 manager 自动选栈              | 「用哪个栈评」本身是评测意图 |
| D3 | manager 只做能力求交，不认识具体栈          | manager 内置栈知识               | 新栈零发版接入        |

## 1. 问题：三处硬编码

当前协议只有 `KernelImplementation { native-c, triton }` 两个值，三个位置把它当成「栈」用，但语义各自漂移。

| 位置                                                             | 现状                                                                  | 问题                                      |
| -------------------------------------------------------------- | ------------------------------------------------------------------- | --------------------------------------- |
| `contracts/api/openapi.json` `KernelImplementation`            | 两个枚举值                                                               | `native-c` 说的是源码方言，`triton` 说的是编译栈，粒度不同 |
| `rvbench-core-rust/src/lib.rs:228` `default_implementation()`  | `k1→native-c`、`k3→triton`                                           | 板上装了什么变成协议常量                            |
| `rvbench-core-rust/src/lib.rs:242` `worker_supports_request()` | 用 `implementations` map 匹配                                          | 方向对，但请求侧仍是封闭 enum                       |
| `rvbench-spacemit-worker/src/backend.rs:58` `supported()`      | `if implementation == NativeC { NATIVE_C_OPS } else { TRITON_OPS }` | 能力表按栈硬编码在 worker 分支里                    |
| `rvbench-ruyi-worker/config/ruyi-k3.toml`                      | `backend = "ruyi-k3"`                                               | 同一块板拆成两个 backend，榜单无法按板卡聚合              |

第三个栈 `ruyiai-sdk` 一进来，这五处全部要动。更糟的是它自带 triton 前端：与 spacemit 的 triton 是同一门语言、不同 runtime，现有 enum 表达不了。

另有一处边界错误：`suite` / `case` 现在装在 `attributes` 里，而 schema 明确写着 `attributes` 是「opaque user metadata, does not change execution or scheduling semantics」。判据引用是评测语义的一部分，不该放在不透明字段里。

## 2. 判据：一个字段只属于一层

| *字段影响什么*          | *归属*               | *例*                                             |
| ----------------- | ------------------ | ----------------------------------------------- |
| *比什么、怎么算对*        | *submit*           | *`op` `shape` `dtype` `seed` 容差 `suite`/`case`* |
| *源码用什么方言写*        | *submit*           | *`source_kind` `entry` `source`*                |
| *源码怎么变成可执行*       | *runtime*          | *gcc flag、triton JIT、buddy-mlir、缓存策略*           |
| *源码由谁执行、绑定哪个 ABI* | *runtime*          | *harness、入口签名、返回约定*                             |
| *跑在哪台机器、哪几个核*     | *worker*           | *`board_id` `affinity` `ai_thread` `taskset`*   |
| *排到哪个队列、能跑多久*     | *manager + worker* | *`kind` 分桶、lease、capacity*                      |

三条反例，用来校准：

- `cpus` 放进 submit → 错。用户不该知道板上有几核，也不该指定。
- 编译 flag 放进 worker → 错。同一台机器上三个栈的 flag 各不相同。
- `TRITON_OPS` 留在 `backend.rs` 的 `if/else` 里 → 错。它是 runtime 的声明，物理上可以放在 worker 仓，归属必须在 provider 模块。

## 3. 概念模型

### 3.1 Submission

一次请求 = 工作负载身份 + 代码 + 所选 runtime + 放置约束 + 执行参数 + 判据引用。

- 工作负载身份不可变，进结果、进 baseline、进去重键。
- 代码是「文本 + 方言 + 入口符号」，不是裸字符串。
- 放置约束只到板卡类别（`backend`），不下到核。
- 执行参数（`warmup` / `repetitions` / `timeout_secs`）由用户请求，runtime 有权 clamp 并回写实际值。

### 3.2 Runtime

一个 runtime 由 worker 部署、向 manager 声明。它有生命周期，但不拥有机器。

```
probe(ctx)     启动时探测：工具链版本、算子覆盖、dtype 覆盖 → RuntimeDecl
accepts(a)     这份 artifact 的方言与入口是否归我处理
prepare(job)   写源码 → 调工具链 → 产出 artifacts + entry + ABI 校验
evaluate(job)  warmup + repetitions → samples_ms + correct
```

七个必需声明字段：

| 字段                         | 含义                                               | 为什么必须在 runtime 上  |
| -------------------------- | ------------------------------------------------ | ----------------- |
| `id` + `version`           | `spacemit-triton@0.3.1`                          | 跨版本数值不可比，必须进结果指纹  |
| `source_kinds`             | 接受的方言                                            | 决定请求能否路由过来        |
| `entry_abi`                | `candidate(a,b)->out` 或 `void f(const float*,…)` | 用户源码与 harness 的契约 |
| `ops` / `dtypes` / `kinds` | 支持矩阵                                             | 准入判定，由 probe 产出   |
| `toolchain`                | gcc 15.2 / triton 3.6.0+spacemit / LLVM rev      | 复现与归因             |
| `isolation`                | 单进程 / 子进程 / 独立 venv / 容器 + 缓存归属                  | 决定并发上限与缓存正确性      |
| `timing_profile`           | `call.median.exclude_prep.v1`                    | 口径不同时 ms 不可比      |

### 3.3 Worker

worker = 一台机器 + N 个执行上下文 + M 个已装 runtime。

- 机器：`board_id`、`arch`、内核版本、总内存。
- 执行上下文：`x100`（affinity 0–7）、`a100`（affinity 8–15 + 写 `/proc/set_ai_thread`）。
- 已装 runtime：RuntimeDecl 列表。

**槽位 slot ≡ (worker, context, runtime)**，是容量与调度的最小单位。一块板提供 2 个上下文 × 3 个 runtime = 6 个槽位，不是 6 台 worker，也不是 1 个不可分的整体。

### 3.4 Manager

manager 只有四件事：校验契约、维护 runtime 目录、排队、把请求匹配到槽位。它不认识 gcc、triton 或 MLIR。

目录（catalog）是集群里所有 worker 声明的聚合视图，用于两件事：

1. 提交时静态校验 `source_kind ↔ runtime` 兼容性，不把错误留到 worker。
2. 控制台的下拉选项。

## 4. 不变量

| 编号 | 不变量                                | 违反后果                          |
| -- | ---------------------------------- | ----------------------------- |
| I1 | submit 不携带机器参数                     | 用户能改核绑定，结果不可比                 |
| I2 | worker 不携带 op 语义常量                 | 每加一个算子要重发 worker              |
| I3 | runtime 不决定跑在哪                     | 同一份源码无法换机器复测                  |
| I4 | 匹配只依赖声明，不依赖推断                      | `default_implementation` 就是反例 |
| I5 | 结果必带 runtime 指纹与 context           | 跨栈分数混进同一榜                     |
| I6 | `(source_kind, runtime)` 兼容性在提交时校验 | 错误要到 worker 才暴露，浪费租约          |
| I7 | 加 runtime 不改协议类型                   | 每次加栈都要发版                      |
| I8 | 计时口径进结果，跨口径不比较                     | ms 数字看似可比，实则不同                |

### 5.5 内部 SPI（worker 侧）

```rust
pub struct ExecutionContext {
    pub id: String,              // "a100"
    pub cpus: Option<String>,    // "8-15"
    pub ai_thread: bool,         // 写 /proc/set_ai_thread
    pub env: BTreeMap<String, String>,
}

pub struct Prepared {
    pub dir: PathBuf,
    pub entry: EntryPoint,       // 符号 + ABI 校验结论
    pub artifacts: Vec<Artifact>,
    pub fingerprint: Fingerprint,
}

pub trait RuntimeProvider: Send + Sync {
    fn decl(&self) -> &RuntimeDecl;
    fn probe(&self, ctx: &ExecutionContext) -> Result<RuntimeDecl>;
    fn accepts(&self, artifact: &Artifact) -> bool;
    fn prepare(&self, job: &JobSpec, ctx: &ExecutionContext, dir: &Path) -> Result<Prepared>;
    fn evaluate(&self, job: &JobSpec, prepared: &Prepared) -> Result<PhaseResult>;
}

pub fn admit(worker: &WorkerView, req: &JobRequest) -> Result<Placement, RejectReason>;
```

| 方法         | 输入             | 输出          | 调用方         | 禁止     |
| ---------- | -------------- | ----------- | ----------- | ------ |
| `decl`     | —              | 静态声明        | 注册、目录       | 读机器状态  |
| `probe`    | context        | 刷新后的声明      | 启动、定时       | 执行用户代码 |
| `accepts`  | artifact       | bool        | 准入          | 做编译    |
| `prepare`  | job + context  | Prepared    | 派发后         | 选核、改队列 |
| `evaluate` | job + prepared | PhaseResult | prepare 成功后 | 重新编译   |

`Placement` = `{slot: {worker, context, runtime}, runtime_version, timing_profile}`。

### 5.6 拒绝原因

| 码                                      | 触发                  | 何时报              | 可重试    | 用户对策              |
| -------------------------------------- | ------------------- | ---------------- | ------ | ----------------- |
| `BACKEND_MISMATCH`                     | 声明里没有该板卡            | 提交               | 否      | 改 `backend`       |
| `KIND_UNSUPPORTED`                     | 槽位不接该 kind          | 提交               | 否      | 换 runtime         |
| `RUNTIME_NOT_INSTALLED`                | 集群无此 id             | 提交               | 否      | 查 `/runtimes`     |
| `RUNTIME_NOT_READY`                    | 有声明但 `ready=false`  | 提交               | 是（等恢复） | 看 `evidence`      |
| `SOURCE_KIND_UNSUPPORTED`              | 方言不在 `source_kinds` | 提交               | 否      | 换写法或换栈            |
| `OP_UNSUPPORTED` / `DTYPE_UNSUPPORTED` | 能力矩阵不覆盖             | 提交               | 否      | 换算子或 dtype        |
| `VERSION_PINNED_MISSING`               | 钉了不存在的版本            | 提交               | 否      | 去掉 pin            |
| `ABI_MISMATCH`                         | 入口签名不符              | prepare          | 否      | 按 `entry_abi` 改签名 |
| `TOOLCHAIN_FAILED`                     | 编译失败                | prepare          | 否      | 看 artifacts 里的日志  |
| `TIMEOUT`                              | 阶段超时                | prepare/evaluate | 是      | 调 `timeout_secs`  |
| `CONTEXT_BUSY`                         | 槽位满                 | 派发               | 是      | 排队即可              |


前七条在提交时就能给出，这是 I6 的价值：不浪费一次租约。

## 6. 三个 provider 的实现要点

| 项 | spacemit-ep | spacemit-triton | ruyiai-sdk |
|---|---|---|---|
| `source_kinds` | `[c]` | `[python, triton]` | `[triton, mlir]` |
| 入口 ABI | `void f(const float*, const float*, float*, int)` | `def candidate(a,b) -> Tensor` | 同 triton，或 MLIR `func` |
| prepare | `gcc -O3 -fno-fast-math` + `-lm` | 写 `harness.py` + `candidate.py`，跑一次冒烟 | buddy-mlir → LLVM → `.so`，需固定 `LLVM_SYSPATH` |
| 产物 | `candidate.c` `harness.c` ELF `compile-manifest.json` | 加 `triton-cache/**` | 加 `.so` 与 lowering 中间件 |
| 隔离 | 单进程 | 子进程 | 独立 venv（py3.12/3.13） |
| 计时 | harness 内 `clock_gettime` | harness 内，口径需与 ep 对齐 | 同左，须排除 lowering |
| 主要失败面 | 编译错、段错误 | JIT 超时、缓存污染 | 缺 LLVM、Python 版本不符 |

三者 ABI、隔离、计时都不同。这是「runtime 必须是可注册对象」的实证：worker 只需要启动一个 provider，不需要知道它怎么跟源码对接。

## 7. 调度与容量

- 容量单位是槽位：`{context, runtime, capacity}`。K3-1 现状 = 2 上下文 × 3 runtime，每槽 capacity 1。
- manager 只按槽位匹配，不指定 context；context 由 worker 在 `admit` 后本地选定（`performance → a100`，其余 → x100）。这是 v1 的简化，理由是 pull 模式下 worker 更清楚当前占用。
- 租约仍 30s，轮询 10s，不变。
- 同一槽位的并发由 `isolation.mode` 决定：`in_process` 串行，`subprocess` 可并行但受 `capacity` 约束。

## 8. 迁移

| 阶段 | 改动 | 可回滚点 |
|---|---|---|
| P0（不改 wire） | worker 内部拆 `Hardware` / `RuntimeProvider` / `Registry`；能力表从 `backend.rs` 挪进 provider；ruyi worker 的 `backend` 改回 `k3` | 单仓 revert，协议未动 |
| P1（协议 minor） | 加 `runtime` `source_kind` `entry` `suite` `case`；`implementation` 标记 deprecated；worker 注册加 `contexts` `runtimes` `slots` | 老 cli 仍发 `implementation`，manager 双向映射 |
| P2（行为切换） | `admit` 改查 `slots`；删 `default_implementation`；结果写指纹；榜单按 runtime 分组 | 保留 `environment.implementations` 生成逻辑一个版本 |
| P3（清理） | 删 `implementation` 与 legacy 字段 | 不可回滚，需等 P2 稳定一个版本 |

| 组合 | 行为 |
|---|---|
| 新 worker × 老 manager | worker 同时写 legacy 字段；老 manager 只看到 default runtime，不报错 |
| 老 worker × 新 manager | 无 `runtimes[]` → 回退 `backend` 隐式映射，标 `legacy: true` |
| 新 cli × 老 manager | 发 `runtime` 会被 `additionalProperties:false` 拒；cli 提供 `--legacy` 写 `implementation` |
| 老 cli × 新 manager | `implementation` 映射到 runtime id，行为不变 |

## 9. 取舍

| 选择 | 备选 | 为什么这样选 |
|---|---|---|
| runtime 由 submit 选，允许留空 | manager 自动选 | 「用哪个栈评」是评测意图；留空时取槽位默认并记录实际值 |
| runtime 在板端编译 | 独立编译服务 | 产物必须与板端 ABI 一致，远程编译把网络变成新失败源 |
| 版本按 major.minor 调度 | 全版本精确匹配 | 否则每个 patch 都要单独占一个槽位 |
| 声明来自 probe | worker 自报 | 自报可以虚标能力，probe 有 evidence sha |
| 扁平请求结构 | 立刻嵌套化 | `spec` / `baseline` / `cli` 都按扁平消费，嵌套化单独一轮 |

## 10. 开放问题

1. `timing_profile` 需要一份正式定义：预热归属、同步点、统计量、是否含分配。三个栈现在各写各的。
2. 是否允许 submit 指定 context（`x100` vs `a100`）。允许会让分数更细，也会让用户承担选核知识。
3. 私有 runtime 的注册审批：谁能往集群里装栈。当前 `WorkerRegistration` 无审批环节。
4. `source_kind = mlir` 时 `entry` 的语义：是 MLIR 函数名，还是 lowering 后的符号。
5. 结果去重键是否要包含 runtime：同一 `request_sha256` 在两个栈上是两次观测，不能合并。
