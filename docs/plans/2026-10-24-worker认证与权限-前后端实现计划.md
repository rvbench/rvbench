# worker 认证与权限（前后端）实现计划

状态：**已实施（2026-10-24，W0–W4 代码完成；上线灰度按 §6 执行，依赖真实集群）** ｜ 依赖：[用户体系](2026-10-24-用户体系-前后端实现计划.md) M0（Permission / 中间件 / Principal） ｜ 关联：[设计与架构](../specs/2026-10-24-用户身份与权限-设计与架构.md)

本计划覆盖 worker 的凭据、归属、认领与调度可见性，含 console 的 `#workers` 管理面与独立的 `/claim` 认领页。人的登录、角色、审计见用户体系计划。

## 0. 交付面

| 面 | 交付物 | 仓 |
|---|---|---|
| 后端 | `workers` / `worker_claims` 表；`/workers` 5 个管理端点；`/cluster/workers/claim` 2 个机器端点；`/claims` 3 个确认端点；`/cluster/*` 挂 `worker` 角色；`allocate()` 私有过滤 | `rvbench-official-manager` |
| 前端 A | console 新增 `#workers` tab：列表、筛选项、创建模态、token 一次性展示、轮换、删除、drain | `rvbench-core-rust/webui/console.html` |
| 前端 B | `/claim` 独立页：短码输入、待确认卡片、确认/拒绝、结果态 | `rvbench-official-manager`（内嵌 HTML） |
| worker | `manager_token` 读取优先级、5 处请求带 header、无 token 时的 claim 客户端、token 落盘 | `rvbench-spacemit-worker` |
| CLI | `rvbench worker login / status / logout` | `rvbench-cli` |
| 契约 | 6 个 schema 进正本（`WorkerRecord` 等） | `rvbench`（主仓） |

**不做**：owner 转交（v1.1）、worker token 过期与自助续期（v1.1）、按 worker 计费/配额。

## 1. 依赖与顺序

```
Plan 1  M0 ──┬─→ W0 ─→ W1 ─→ W3 ─→ W4
             │         │
             └─ M1 ────┴─→ W2（claim 需要登录）
```

| 阶段 | 依赖 | 说明 |
|---|---|---|
| W0 | M0 | 只用到 `Permission`、`AuthState`、错误码 |
| W1 | W0 | 可用 `worker_tokens[]` bootstrap，**不需要 GitHub 登录**，可与 M1 并行 |
| W2 | W0 + M1 | claim 的确认必须有人能登录 |
| W3 | W1 + M2 | 私有过滤需要 `owners[job]`，来自 M2 |
| W4 | W1 + W3 + M1 | UI 需要 `me` 与 worker 数据 |

W1 先行的价值：三块在役板子在用户系统上线前就切到「每台一份 token」，把假 worker 抢单这条路先堵上。

### W1 预置 token 路径（约 1.5 天）

后端：

| 端点 | 行为 |
|---|---|
| `POST /workers` | `{worker_id, visibility}`；private → owner 为调用者；public → 仅 admin，owner `org:rvbench`；返回 `WorkerCreated`（含明文 token） |
| `GET /workers` | 自己的 + public；admin 全部；含 `pending` 记录 |
| `GET /workers/{id}` | owner / admin / public 可读；不含 token |
| `POST /workers/{id}/tokens` | 轮换；旧 token 立即失效 |
| `DELETE /workers/{id}` | 有在途 assignment → 409 |

中间件：

| 改动 | 说明 |
|---|---|
| `src/auth/mod.rs` | 增加 `rvbw_` 前缀分流：查 `workers` → 主体 `worker:<id>`、`roles=["worker"]`；未命中查 bootstrap 配置 |
| `src/lib.rs` | `/cluster/workers/register` 挂 `worker:register`；claim/ack/renew/events 挂 `worker:execute`；drain 挂 `worker:manage:self` 或 `:all` |
| `src/lib.rs` | `GET /cluster/workers` 输出加 `owner` / `visibility`，裁掉 `url`（admin `?full=true`） |

worker 侧：

| 文件 | 改动 |
|---|---|
| `src/lib.rs` | `Config.manager_token: Option<String>` 与 `allow_claim: bool` |
| 同上 | token 解析顺序：`RVBENCH_WORKER_TOKEN` env → `~/.config/rvbench/worker-token` → `config.manager_token` |
| 同上 | 5 个 call site 统一加 `Authorization: Bearer`（抽一个 `fn manager_request()`） |
| 同上 | 401 时打印「token 无效或被撤销」；403 时打印「worker_id 与 token 的 id 不一致」 |

验收：

```sh
# 生成并下发
TOKEN=$(rvbench --base http://127.0.0.1:18800 worker create --id k3-4 --private --print-token)
# 板上
rvbench-worker --config config.json   # manager_token 生效，注册成功
curl -s localhost:18800/cluster/workers | jq '.[] | select(.worker.worker_id=="k3-4") | {owner,visibility}'
# 撤销后
curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:18800/cluster/assignments/claim \
  -H "Authorization: Bearer $TOKEN" -d '{}'   # 401
```

### W2 首次认领（约 2 天）

后端：

| 端点 | 行为 |
|---|---|
| `POST /cluster/workers/claim` | 无凭据；限流；`worker_id` 冲突 409；返回 code/device_code/URL/TTL |
| `GET /cluster/workers/claim/{device_code}` | 202 pending / 200 approved+token / 410 denied·expired |
| `GET /claims` | 登录用户看待确认列表 |
| `POST /claims/{code}/approve` | 绑定 owner=确认者；visibility 默认 private，public 需 admin；token 存库，等 worker 取走 |
| `POST /claims/{code}/deny` | 410 |

| 细节 | 做法 |
|---|---|
| code | 8 字符 `XXXX-XXXX`，字符集 `A-HJ-NP-Z2-9`；`worker_claims.code` 唯一 |
| 并发确认 | `UPDATE ... WHERE status='pending'` 判断影响行数，失败 409 |
| token 只取一次 | 轮询返回后把 `token_sha256` 标记 `delivered_at`，再次轮询 410 |
| 清理 | 启动与每小时删除 `expires_at < now-24h` 的记录 |

worker 侧：

| 文件 | 改动 |
|---|---|
| `src/claim.rs` | 无 token 且 `allow_claim` 时：POST claim → 打印 `打开 <url> 输入 <code>` → 每 5s 轮询 → 拿 token → 写 `worker-token`（0600）→ 转正常注册 |
| `src/lib.rs` | `open()` 里决定走 token 还是 claim；claim 失败不阻塞进程（打印原因并退出） |

前端 B（`/claim` 独立页）：

见 §3.4。

验收：

```sh
# 模拟 worker
DEV=$(curl -s -X POST localhost:18800/cluster/workers/claim -H 'content-type: application/json' \
  -d '{"worker_id":"k3-9","board_id":"K3-9","backend":"k3","kinds":["correctness"]}' | jq -r .device_code)
curl -s localhost:18800/cluster/workers/claim/$DEV | jq .status        # pending
# 浏览器登录后 approve，再轮询
curl -s localhost:18800/cluster/workers/claim/$DEV | jq '{status,token}'  # approved + rvbw_
curl -s localhost:18800/cluster/workers/claim/$DEV | jq .status        # 410（token 已取走）
```

## 3. 前端设计

### 3.1 两个面，为什么分开

| 面 | 载体 | 使用者 | 理由 |
|---|---|---|---|
| `#workers` 管理 | `console.html`（协议仓内嵌） | 已登录用户 / admin | 与节点状态、任务结果同屏，复用现有样式 |
| `/claim` 认领 | manager 内嵌独立 HTML | 正在上板的人 | 加载快、不依赖 status 数据、改版不触发协议仓 rev；且手机上打开更轻 |

`/claim` 不放进 console 的 hash 路由，是因为它需要从板子日志里手输 URL，路径越短越好；而且认领是一次性动作，没必要加载整个控制台。

### 3.2 `#workers` tab 布局

```
┌─ 节点管理 ──────────────────────────────────────────────── [＋ 添加 worker] ┐
│ [全部 6] [我的 2] [公开 4]            ⌕ 搜索 worker_id                      │
│ ┌──────────┬────────────┬────────┬──────┬──────────┬──────────┬─────────┐  │
│ │ worker   │ owner      │ 可见性 │ 状态 │ 最近心跳 │ 当前任务 │ 操作    │  │
│ ├──────────┼────────────┼────────┼──────┼──────────┼──────────┼─────────┤  │
│ │ k3-1     │ org:rvbench│ 公开   │ ● 在线│ 2s 前    │ 1        │ drain   │  │
│ │ k3-4     │ c4y        │ 私有   │ ● 在线│ 5s 前    │ 0        │ ⋯       │  │
│ │ k3-9     │ —          │ 私有   │ ○ 待认领│ —      │ —        │ 撤销    │  │
│ └──────────┴────────────┴────────┴──────┴──────────┴──────────┴─────────┘  │
└───────────────────────────────────────────────────────────────────────────┘
```

| 列 | 数据 | 备注 |
|---|---|---|
| worker | `worker_id` | 等宽字体 |
| owner | `login` 或 `org:rvbench` | hover 显示 `sub` |
| 可见性 | 徽章：公开 `--green` / 私有 `--muted` | |
| 状态 | `active` 在线=绿点 / 离线=灰点 / `pending`=空心圈 / `revoked`=划线 | 与 `last_seen` 推导 |
| 最近心跳 | 相对时间 | 超过 30s 标琥珀 |
| 当前任务 | 从 `/cluster/workers` 的 assignments 取 | 只对 admin 显示详情 |
| 操作 | 按权限渲染 | drain / 轮换 / 删除 |

筛选项「全部 / 我的 / 公开」是客户端过滤，数据一次拉全（≤ 200 条）。

### 3.3 创建模态

```
┌─ 添加 worker ────────────────────────────────┐
│ worker_id  [k3-4                    ]        │
│            小写字母、数字、- 和 _，2–64 字符  │
│                                              │

```

创建成功后**同一个模态**切换为 token 展示态：

```
┌─ 已创建 k3-4 ────────────────────────────────┐
│ ⚠ token 只显示这一次，关闭后无法再查看         │
│ ┌──────────────────────────────────────────┐ │
│ │ rvbw_9f2c…（完整 52 字符，等宽，可选中）  │ │
│ └──────────────────────────────────────────┘ │
│ [复制]                                       │
│                                              │
│ 下一步：把 token 写到板子的                    │
│ ~/.config/rvbench/worker-token（0600），      │
│ 或 `rvbench worker login` 让板子自己领。      │
│                                              │
│                                       [完成] │
└──────────────────────────────────────────────┘
```

| 行为 | 规则 |
|---|---|
| 关闭 | 若未点「完成」而是点遮罩/Esc，弹二次确认「token 不会再次显示」 |
| 复制 | `navigator.clipboard.writeText`，失败降级为选中文本 |
| 刷新页面 | token 丢失，只能轮换；文案提前说明 |
| 权限 | `visibility=public` 选项对非 admin 隐藏（不是置灰，避免试探） |

独立 HTML，约 200 行，内联样式，复用同一套 CSS 变量（复制一份，不跨文件引用）。

```
┌──────────────────────────────────────────────┐
│ [rv] rvbench            c4y ▾  [退出]        │
├──────────────────────────────────────────────┤
│  认领 worker                                  │
│  输入板子日志里的 8 位短码，确认后它会绑定到你  │
│                                              │
│  [ K3F9-Q2T4 ]              [查找]           │
│                                              │
│  ┌────────────────────────────────────────┐  │
│  │ worker_id   k3-4                       │  │
│  │ board       K3-4-32G                   │  │
│  │ backend     k3                         │  │
│  │ kinds       correctness                │  │
│  │ 来源 IP     10.18.26.5                 │  │
│  │ 请求时间    2 分钟前（8 分钟后过期）     │  │
│  │                                        │  │
│  │ 可见性   (•) 私有  ( ) 公开             │  │
│  │                                        │  │
│  │ 只在你亲自上架这块板子时确认。           │  │
│  │                        [拒绝]  [确认]  │  │
│  └────────────────────────────────────────┘  │
│                                              │
│  待确认（3）                                  │
│  · k3-9 / K3-9 / 10.18.26.9 / 1 分钟前       │
│  · k1-2 / K1-2 / 10.18.60.170 / 3 分钟前     │
└──────────────────────────────────────────────┘
```

| 状态 | 渲染 |
|---|---|
| 未登录 | 顶部横幅「登录后确认」，整页内容置灰；登录按钮跳 `/auth/login?redirect=/claim` |
| 无 code 参数 | 只显示短码输入 + 待确认列表 |
| code 无效/过期/已处理 | 输入框下方红字，列表刷新 |
| 确认成功 | 卡片替换为「已绑定到 c4y（私有）· worker 将在几秒内拿到 token」+「继续认领」 |
| 非 admin 选公开 | 选项不渲染 |

交互细节：

- 短码输入自动大写、自动补 `-`、过滤 `0O1I`（输入时直接丢弃）。
- 待确认列表每 10 秒刷新；页面失焦（`document.hidden`）时暂停。
- 来源 IP 用等宽字体，便于和人核对。
- 确认按钮为实心 accent；拒绝为文字按钮，避免误点。

### 3.7 空态与错误态

| 场景 | 文案 | 动作 |
|---|---|---|
| 没有 worker | 还没有 worker。添加一台，或在板上运行 `rvbench worker login` | 添加 |
| 只有别人的私有 worker | 没有可见的 worker | 无 |
| token 创建失败 409 | worker_id 已被占用 | 改 id |
| 轮换后 worker 掉线 | 已轮换。板子需要更新 token 才能重新上线 | 复制新 token |
| claim 过期 | 短码已过期，请让板子重新发起认领 | 刷新 |
| claim 被他人确认 | 这条认领已被处理 | 刷新 |
| 无权限 drain | 只有 owner 或管理员可以下线该 worker | 无 |

## 6. 发布与回滚

| 步 | 内容 | 顺序约束 |
|---|---|---|
| 1 | manager 上 `workers` 表与端点（`worker_tokens` 仍可用） | 先于 worker |
| 2 | 三块板改配置用 `rvbw_` token，逐台重启 | 每台重启后 `GET /cluster/workers` 应仍列出 |

## 9. 评审记录（2026-10-24）

结论：**通过，可实施**。依赖（用户体系 M0–M3）已就位。修订与实施注意：

1. §0「6 个 schema」计数不准：`/workers` 与 `/claims`、`/cluster/workers/claim` 路径实际引用 12 个 schema（WorkerRecord/WorkerCreated/WorkerToken/CreateWorkerRequest/WorkerVisibility/OwnerRef/ClaimView/ClaimCode/WorkerClaimRequest/WorkerClaimChallenge/WorkerClaimPoll/ApproveClaimRequest），契约合并按 12 个计。
2. **架构补充——WorkerRegistry 内存快照**：`allocate()` 在 `store.tx` 事务内（同步、禁 IO），不能查 auth.sqlite；worker 心跳 2–3 秒一次也不宜直写库。新增 `WorkerRegistry`（manager 内存）：启动时从 `workers` 表 + `worker_tokens[]` bootstrap 装载，create/rotate/delete/approve 写穿，register 更新内存 `last_seen` 并由后台任务每 10 秒落库（设计 §4.3）；`allocate()`、可见性过滤、token 分流都读快照。
3. **通道开关独立于 auth.mode**（设计 §2/D6）：`check()` 不能对 worker 权限走「mode=off 即放行」的短路——只要「库里有有效记录或 `worker_tokens[]` 非空」，`/cluster/*` 就强制 worker 凭据，即使 `auth.mode=off`；两者都空时保持现状匿名放行（灰度）。
4. claim 的 token 交接需要瞬态明文：`workers` 表只存 sha256，approve 与 worker 首次轮询之间明文必须暂存（`worker_claims.approved_token`，交付后清空）。窗口分钟级，可接受。
5. CLI 既有 `worker` 子命令组是直连模式 job 操作；按计划在其下扩展 `create/login/status/logout`（目标 manager），动作不冲突。
6. 权限矩阵补充（设计 §2）：`admin` **不含** `worker:register`/`worker:execute`（人不能冒充机器）；`worker` 主体权限为 `[worker:register, worker:execute, worker:manage:self]`（无 `metrics:read`）。`Principal::has()` 改为只看派生权限表，不再 admin 直通。
7. 既有 manager 测试直接调 `m.claim()`：registry 为空时行为必须与现在完全一致（未知 worker 视为 public）。
